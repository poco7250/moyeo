# moyeo PRD — 친구 모임 관리 웹앱

## Context

친구 모임은 보통 **1차 밥 → 2차 볼링 or 보드게임** 패턴으로 굴러간다. 이때 매번 반복되는 귀찮음이 있다.

- 단톡방에서 "누구 와?" 물어보고 답 안 하는 사람 쫓아다니기
- "어디서 볼까?" 하면 맛집 링크만 수십 개 쏟아지고 결정은 흐지부지, 2차 장소는 당일에 급하게 찾기
- 1차만 온 사람, 2차부터 온 사람 섞여서 정산이 꼬임
- "꼴찌가 2차 쏘기" 같은 벌칙을 하지만 결과가 정산에 수동으로 반영됨
- 사다리·꽝뽑기는 각자 다른 앱을 켜서 하고, 기록은 안 남음

**한 줄 정의:** "모임 공지 → 장소 정하기 → 참석 → 놀기(게임) → 정산"을 **하나의 링크**로 끝내는 모바일 웹앱.

**핵심 차별점:** **게임 결과가 정산에 자동으로 연결된다.** (토스 N빵·사다리 앱 같은 단일 기능 앱과의 차이)
- 실제 모임 습관대로 **게임은 "누가 벌칙을 받는지"만 먼저 정하고**, 벌칙 금액 조건은 **지출이 나온 뒤** 호스트가 **지출 한 건을 골라** 정한다. 조건만 넣으면 부담액·송금 안내 목록("누가 누구에게 얼마")은 자동 계산된다. **실제 송금은 토스·카카오페이 등 앱 밖에서 한다(E1)** — 앱은 송금 여부를 기록하지 않는다.
- 정산을 확정한 뒤에 지출·벌칙이 바뀌어도 막지 않는다. **재확정 + 변경 이력 + 이전 확정 대비 1인당 변동액 안내**로 정리하므로 "이미 확정해서 못 고쳐"가 없다.

## 1. 목표 & 지표

| 구분 | 목표 | 지표 (측정 방법) |
|---|---|---|
| 참석 확인 | 단톡방 "누구 와?" 제거 | 모임 생성 후 24h 내 응답률 ≥ 80% (`Attendance` 응답 시각 기준) |
| 장소 결정 | 단톡방 "어디서 봐?" 제거 | 투표 시작 → 장소 확정까지 시간 중앙값, 투표 참여율(투표한 멤버 ÷ 그룹 멤버) |
| 정산 | 모임 끝나고 10분 안에 정산 확정 | 모임 종료 → **최초 확정**(`SettlementRevision` 1번 `confirmedAt`)까지 시간 중앙값 ≤ 10분. "모임 종료" 시각 = **최초 확정 전 마지막 지출 등록 시각**(`Expense.createdAt` 최댓값, 차수 종료 시각을 따로 저장하지 않으므로 대리 지표 — 4차 m10). 송금은 앱 밖이라(E1) 송금 완료까지는 측정하지 않는다. 보조 지표(모니터링, 목표 없음): 재확정 발생 모임 비율(리비전 ≥ 2인 모임 ÷ 확정된 모임) |
| 재미 | 게임을 moyeo 안에서 | 모임당 게임 실행 횟수, 게임→정산 연동 비율 = **최종 리비전** 확정 시점에 벌칙이 `APPLIED`인 게임 ÷ `penaltyKind = MONEY`인 게임(각 게임의 **비무효 최신 회차**만 셈 — `VOIDED` 원 회차·`CANCELED` 회차 제외) |
| 리텐션 | 같은 그룹의 재사용 | 그룹당 월 모임 생성 수, 4주 재방문율 |

**Non-goal (지금은 안 함):**
- 장소 예약/결제 대행 — 장소를 *정하는* 것까지만, 예약은 사용자가 직접
- 송금 실행·송금 완료 추적 — 앱은 "누가 누구에게 얼마"만 안내하고, 송금은 토스·카카오페이 등 앱 밖에서 한다(E1, S-6 폐지)
- 공개 모임 매칭(소모임·문토류)
- 채팅 기능 — 단톡방 대체 X, 단톡방에 링크를 뿌리는 구조

## 2. 타겟 & 페르소나

| 페르소나 | 특징 | 이탈 요인 / 대응 |
|---|---|---|
| **총무형(호스트)** — 핵심 사용자 | 모임 만들고 정산까지 떠안는 사람. 가장 큰 페인 보유 | 정산이 수동이면 안 씀 → 벌칙 자동 반영·송금 최소화 |
| **참여형(게스트)** | 링크 눌러 참석만 누르고 싶은 사람 | **가입 폼을 강요하면 이탈** → 카카오 원탭 로그인으로 진입 비용 최소화 |

- 규모: 4~12명 고정 친구 그룹, 월 1~4회 모임.

## 3. 핵심 사용자 흐름

```
[호스트] 그룹 생성 → 모임 생성(날짜/차수) → 차수별 장소 바로 지정 or 후보 투표 열기 → 카톡으로 링크 공유
[게스트] 링크 접속 → 카카오 로그인(원탭) → 그룹 자동 가입 → 차수별 참석 응답 + 장소 후보 추가·투표
        ↓ (마감 전 미응답자 리마인드, 투표 마감 시 장소 자동 확정)
[당일]  체크인 → 사다리·꽝뽑기(벌칙자만 결정) / 2차 볼링 점수 입력 → 차수별 지출 등록
        ↓ (게임 결과 → "벌칙자: 민수(사다리 꽝)" 확정, 금액 조건은 아직 없음)
        ↓ (지출 등록 뒤 호스트가 벌칙 조건 입력 → "민수: 2차 볼링비(지출 1건) 30% 부담" 정산 자동 반영)
[종료]  조건 미설정 벌칙 정리(조건 입력 or 금액 벌칙 없음) → 정산 확정(리비전 1) → 송금 안내 목록 공유
        → 각자 앱 밖(토스·카카오페이 등)에서 송금(E1, 앱은 송금 여부 기록 안 함) → 기록/명예의 전당
        ↓ (확정 후 지출·벌칙·참석 수정 / 다시 돌리기 → 정산 "재확정 필요(REOPENED)" + 변경 로그 기록)
[재확정] 호스트가 다시 확정(리비전 +1) → 새 리비전 전체 송금 안내 + 이전 확정 리비전 대비 1인당 변동액
        ("이미 보냈다면 변동분만 앱 밖에서 더 보내거나 돌려받으세요") → 실시간 알림·공유 문구
```

- **호스트** = 모임을 만든 사람(`Meeting.hostMemberId`, D4). 이 문서의 "호스트"는 모두 이 정의를 따른다.

## 4. 기능 요구사항

우선순위: **P0 = MVP 필수 / P1 = 출시 직후 / P2 = 이후**. 기능 ID는 다른 문서·태스크가 참조하므로 재번호하지 않는다(표 순서 ≠ 번호 순서일 수 있음).

### 4.1 그룹(크루)

| ID | 기능 | 우선순위 |
|---|---|---|
| G-1 | 그룹 생성, 초대 링크 발급(만료/재발급) | P0 |
| G-2 | 멤버 목록, 그룹 내 닉네임/프로필 이모지 | P0 |
| G-3 | **카카오 로그인** 후 초대 링크로 그룹 자동 가입(카카오 닉네임·프로필 기본값, 그룹 내 닉네임 변경 가능) | P0 |
| G-4 | 역할: 방장 / 총무 / 멤버 (모임 단위 "호스트"와는 별개 — 4.2 호스트 정의 참고) | P1 |
| G-5 | 그룹 기본 송금 계좌·토스/카카오페이 링크 저장 | P1 |
| G-6 | 카카오 계정 없는 친구용 임시 게스트(닉네임 + 기기 토큰, 참석 응답만 가능) | P2 |

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| G-1 | Given 로그인한 사용자 / When 그룹을 생성하면 / Then 생성자는 그 그룹 멤버가 되고 만료 시각이 있는 초대 링크 토큰이 발급된다. Given 초대 링크를 재발급하면 / Then 이전 토큰으로 접속 시 "만료된 링크" 응답을 받는다. |
| G-2 | Given 그룹 멤버 / When 멤버 목록을 조회하면 / Then 각 멤버의 그룹 내 닉네임·프로필 이모지가 반환되고, 비멤버가 조회하면 403(`NOT_GROUP_MEMBER`)을 받는다. |
| G-3 | Given 미로그인 사용자가 유효한 초대 링크로 접속 / When 카카오 로그인을 마치면 / Then 원래 초대 링크로 돌아가 그룹에 자동 가입되고 그룹 닉네임 기본값은 카카오 닉네임이다. Given 이미 가입된 멤버 / When 같은 링크로 다시 들어오면 / Then 중복 가입 없이 그룹 홈으로 이동한다. |

### 4.2 모임 & 참석

| ID | 기능 | 우선순위 |
|---|---|---|
| M-1 | 모임 생성: 제목, 날짜·시간, 메모 (장소는 차수별로 정함 — 4.3 참고) | P0 |
| M-2 | **차수(라운드) 구성**: 1차 밥 / 2차 볼링 / 3차 보드게임 등 템플릿 제공 | P0 |
| M-3 | **차수별 참석 응답**: 참석 / 불참 / 미정 + "늦참(2차부터)", "1차만" | P0 |
| M-4 | 응답 마감 시간, 현황판(누가 왔고 누가 안 눌렀는지) | P0 |
| M-5 | 날짜 후보 투표(When2meet식) — 날짜 미정일 때 | P1 |
| M-6 | 미응답자 리마인드(카톡 공유 문구 생성 / 웹 푸시) | P1 |
| M-7 | 당일 체크인(도착 체크) → 실제 참석자 확정 | P1 |
| M-8 | 노쇼 기록 → 통계 반영 | P2 |

> 설계 포인트: **참석 데이터 = 정산 데이터의 기본값.** 차수별 참석자가 그대로 정산 분배 대상이 된다. 그래서 지출이 있는 차수의 참석 변경은 금액 영향 변경이다(정산 확정 후면 `REOPENED`, 4.5).

> 설계 포인트: **호스트 정의(D4).** MVP에서 호스트 = **모임을 만든 사람**(`Meeting.hostMemberId`, 생성 시 고정, 위임 없음). M-4 대리 수정, P-2·P-4 장소 확정·재투표, R-9 벌칙 조건·면제, R-0 게임 시작·R-1 사다리 결과 공개·R-10 게임 취소·R-5 다시 돌리기·게임 종료(진행자와 함께, E3·5차 M-A), S-10 정산 확정·재확정 권한은 모두 이 호스트 기준이다. 그룹 역할(G-4 방장/총무, P1)은 그룹 단위라 별개이며, 도입 시 "총무에게 호스트 권한 위임" 같은 연결은 오픈 이슈 15에서 정한다.

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| M-1 | Given 그룹 멤버 / When 제목·날짜·시간·메모로 모임을 생성하면 / Then 모임이 그룹에 등록되고 모임 상세 링크가 반환되며, 생성자가 `Meeting.hostMemberId`로 저장되고 `Settlement`가 `DRAFT`로 함께 생성된다. 제목·날짜 누락 시 400과 필드 에러를 받는다. |
| M-2 | Given 모임 생성 화면 / When "밥→볼링" 템플릿을 고르면 / Then 1차(밥)·2차(볼링) 차수가 순서대로 생성되고, 각 차수의 장소 상태는 `UNDECIDED`다. |
| M-3 | Given 차수가 2개인 모임 / When 멤버가 "늦참(2차부터)"을 고르면 / Then 1차는 불참, 2차는 참석으로 저장된다. "1차만"은 그 반대로 저장된다. 같은 멤버가 다시 응답하면 기존 응답이 갱신된다(차수당 1건). |
| M-4 | Given 응답 마감 시간이 지난 모임 / When 멤버가 응답을 바꾸려 하면 / Then 거부된다(호스트 = 모임 생성자의 대리 수정은 허용, 그 외 멤버 403). 현황판은 차수별로 참석/불참/미정/미응답 멤버 목록을 보여준다. |

### 4.3 장소 결정

| ID | 기능 | 우선순위 |
|---|---|---|
| P-1 | **장소 검색·후보 등록**: 카카오 로컬 검색으로 장소 검색(결과는 실시간 표시만, 저장 안 함) → 후보 등록 시 `kakaoPlaceId` + 사용자가 확정한 **표시 이름(label)**만 저장. 검색 안 되면 이름 + 주소·지도 링크 직접 입력 | P0 |
| P-2 | **차수별 장소 정하기**: 호스트가 바로 확정하거나, 후보 투표를 연다. 투표 중엔 멤버 누구나 후보 추가 가능 | P0 |
| P-3 | **후보 투표**: 복수 선택 가능, 득표 현황 실시간 갱신(누가 어디 찍었는지 공개) | P0 |
| P-4 | **마감 & 확정**: 투표 마감 시 최다 득표 후보 자동 확정, 호스트는 언제든 수동 확정/재투표 가능. 동점이면 호스트가 고름 | P0 |
| P-5 | 확정 장소 노출: 모임 상세·카톡 공유 문구·OG 미리보기에 표시 이름(label) 반영, 카카오맵 지도·길찾기 **URL 링크**(`/link/map/{장소ID}`, `/link/to/{장소ID}`, 직접 입력 장소는 사용자 지도 링크 또는 `/link/search/{검색어}`) | P0 |
| P-6 | 동점 시 룰렛으로 결정(R-3 연동, 결과 이력 공개) | P1 |
| P-7 | **2차 장소 추천**: 확정된 1차 장소 반경 N m 안의 볼링장·보드게임카페·술집을 카테고리 검색으로 후보 제안 (좌표 미저장 제약 — 장소 도메인 규칙 참고) | P1 |
| P-8 | 그룹 단골 장소 저장, 지난 모임 장소에서 바로 후보로 불러오기 | P1 |
| P-9 | 행동형 벌칙 "다음 모임 장소 정하기" 당첨자에게 다음 모임 1차 장소 확정 권한 부여 | P2 |
| P-10 | **중간 지점 추천**: 참석자가 출발지(동네 수준)를 선택 입력 → 중간 지점 근처 후보 제안 | P2 |

> 설계 포인트: **장소는 모임이 아니라 차수(Round)에 붙는다.** 1차 밥집, 2차 볼링장이 다르기 때문. 차수마다 `UNDECIDED(미정) → VOTING(투표 중) → CONFIRMED(확정)` 상태를 따로 갖는다.

**장소 도메인 규칙**
- **저장 범위(보수안, 오픈 이슈 5):** 카카오 FAQ의 "응답 결과 데이터 별도 저장 불허, 실시간 호출만 가능" 안내에 맞춰 카카오 응답에서 저장하는 값은 **`kakaoPlaceId`뿐**이다. 주소·좌표·카테고리·전화번호 등 API 응답 필드는 DB·캐시에 저장하지 않는다.
  - **표시 이름(label):** 후보 등록 시 검색 결과 이름을 기본값으로 채워주고, 사용자가 확인·수정해 확정한 값을 **사용자 입력 데이터**로 저장한다(가게가 이름을 바꾸거나 폐업해도 기록상 이름은 유지). 회색지대이므로 오픈 이슈 5에서 최종 확인.
  - **직접 입력(P-1 폴백):** 사용자가 입력한 이름·주소 텍스트·지도 링크는 사용자 데이터이므로 저장한다(`kakaoPlaceId`는 null).
  - **직접 입력 지도 링크(`manualMapUrl`) 검증:** **`https` 스킴만 허용**, 최대 **2,048자**. `http`·`javascript:` 등 다른 스킴이나 길이 초과면 400(필드 에러). 서버는 이 URL을 호출하지 않고 링크로만 노출한다.
  - **지도·길찾기:** 지도 임베드·좌표 저장 대신 카카오맵 URL 링크로 대체한다 — 지도 `https://map.kakao.com/link/map/{장소ID}`, 길찾기 `https://map.kakao.com/link/to/{장소ID}`. 직접 입력 장소는 사용자가 넣은 지도 링크(`manualMapUrl`)를 쓰고, **없으면 `https://map.kakao.com/link/search/{검색어}`로 대체**한다(검색어 = `manualAddress`가 있으면 그것, 없으면 `label`, URL 인코딩). 대체 링크는 조회 시점에 문자열로 만들 뿐 카카오 API 호출·저장은 없다(출처: https://apis.map.kakao.com/web/guide/).
  - **좌표 기반 기능 영향:** 좌표를 저장하지 않으므로 P-7(1차 장소 반경 추천)·P-10(중간 지점 추천)은 요청 시점에 실시간 조회한 값만 쓰고 저장하지 않는다(P-10 출발지 좌표도 저장하지 않음). 1차 장소 좌표를 실시간으로 얻는 방법은 오픈 이슈 5에 포함(P1/P2라 MVP 영향 없음). 히스토리(H-1)의 "어디서"는 표시 이름(label)으로 남는다.
- **카카오 로컬 프록시:** 장소 검색은 **백엔드가 카카오 로컬 REST API를 매 요청마다 실시간 프록시 호출**한다(REST 키를 클라이언트에 노출하지 않고, 호출량 제한을 서버에서 관리). **검색 결과는 캐싱·저장하지 않고** 응답을 그대로 클라이언트에 전달한다.
- **동시성:** 투표는 `(후보, 멤버)` **유니크 제약**으로 중복을 막고, 마감 처리와 수동 확정이 겹치면 `Round.version` **낙관적 락**으로 먼저 들어온 쪽만 반영한다.
- 상태 전이: `UNDECIDED → CONFIRMED`(바로 확정), `UNDECIDED → VOTING → CONFIRMED`(투표), `CONFIRMED → VOTING`(재투표, 호스트만).

> 설계 포인트: **게임 진행 방식은 각자 폰.** 게임 상태(`WAITING` 대기 → `PLAYING` 진행 → `REVEALED` 공개 → `CLOSED` 종료, `WAITING`/`PLAYING` → `CANCELED` 취소)는 서버가 관리하고 WebSocket으로 모든 참가자에게 브로드캐스트한다(전이 규칙은 아래 게임 상태 전이 표). **진행자** = 게임을 만든 멤버(`GameSession.createdBy`, 호스트일 필요 없음). 다시 돌린 회차의 진행자는 다시 돌리기를 요청한 사람이다(E3).

> 설계 포인트: **게임은 벌칙자만 정하고, 금액은 나중에 정한다.** 실제 모임에서는 게임을 먼저 하고 벌칙 금액은 지출이 나온 뒤 당첨자 기준으로 나누기 때문. 게임 생성 시 금액 조건(`PenaltyRule`)은 만들지 않고, 결과 공개 시 벌칙자별 `Penalty`(`ASSIGNED`)만 생긴다. 금액 조건은 게임 후 호스트가 설정한다(R-9, 4.5).

**공정성 요구사항 (중요)**
- 결과(사다리 연결, 카드 배치)는 **게임 시작 시점에 서버에서 생성**하고, 클라이언트에는 공개 시점 전까지 보내지 않는다.
- 꽝뽑기에서 "카드를 고르는 행위"는 연출이고, 실제 결과는 서버가 미리 섞어둔 배열의 위치로 결정된다. 같은 카드를 동시에 고르면 먼저 도착한 요청이 가져간다 — 카드 선택은 `GameSession` 행 **`PESSIMISTIC_WRITE`**(행 잠금 대기)로 직렬화하고, 같은 카드 충돌은 `(gameSession, pickedSlot)` 유니크로 막아 늦은 쪽은 409(`SLOT_ALREADY_PICKED`)(5차 m2, 기존 "낙관적 락" 대체).
- 실행 시각·참가자·결과를 기록으로 남기고, "다시 돌리기"는 가능하되 **재실행 이력이 모두에게 보인다** (조작 의심 방지 = 친구 사이 신뢰).
- **다시 돌리기 제한:** 같은 회차를 두 번 다시 돌릴 수 없다(`rerunOf` 유니크 — 동시 요청 중 하나만 성공). 정산이 확정된 모임의 금액형 게임도 다시 돌릴 수 있고, 그 순간 정산이 `REOPENED`(재확정 필요)가 되며 변경 로그에 남는다(D2, 기존 N4 차단 방침 대체).
- **다시 돌리기 대상(4차 M7):** 원 회차가 `REVEALED`/`CLOSED`이면서 **비무효 최신 회차**(그 회차를 `rerunOf`로 가리키는 후속 회차가 없음 — 취소된 후속 회차는 `rerunOf`를 비우므로 해당 없음)일 때만 가능. 그 외(`WAITING`/`PLAYING`/`CANCELED`, 이미 후속 회차가 있는 회차)는 409(`GAME_NOT_RERUNNABLE`). 사전 검사를 통과한 동시 요청끼리는 `rerunOf` 유니크 위반으로 늦은 쪽 409(`RERUN_ALREADY_EXISTS`).
- **다시 돌리기 권한·상속(E3, 4차 M1):** 요청 권한 = 원 회차 진행자(`createdBy`) 또는 모임 호스트, 그 외 그룹 멤버는 403(`NOT_GAME_OPERATOR`), 비멤버는 403(`NOT_GROUP_MEMBER`). 새 회차 `createdBy` = 요청자. 새 회차는 원 회차의 `type`·`penaltyKind`·`penaltyNote`·참가자 목록을 **복제**하며 변경할 수 없다(요청 DTO에 해당 필드 없음).
- **다시 돌리기 처리 시점:**
  - 요청 시점: 새 `GameSession`(`WAITING`, `rerunOf` = 원 회차, `applyOrderAt` 상속, 위 항목 복제)만 만든다. 원 회차 `Penalty`·`PenaltyRule`은 **아직 그대로**라 정산 계산에도 계속 들어간다. 대신 금액형이면 새 회차가 `WAITING`/`PLAYING`인 동안 정산 확정이 막힌다(S-10).
  - 새 회차 **결과 공개 시점**(한 트랜잭션): 원 회차 비무효 `Penalty` → `VOIDED`, 원 회차 `PenaltyRule`을 새 회차로 **이관**(`gameSession`만 변경, `setBy`·`updatedAt`은 원래 값 유지 — 조건을 새로 정한 게 아니므로, ChangeLog에 이관 기록), 새 벌칙자 `Penalty`를 원 회차의 **공개 직전 조건 상태**대로 생성 — 규칙 있음 → `APPLIED`, 면제 → `WAIVED`, 미설정 → `ASSIGNED`.
  - **`Penalty` 생성 순서(4차 m3):** 결과 공개(최초·다시 돌린 회차 모두) 시 벌칙자 `Penalty`는 **`memberId` 오름차순으로 insert**한다. 그래서 같은 게임 안 `Penalty.id` 순서 = `memberId` 순서로 결정적이고, D3 초과분 차감 순서(`Penalty.id` 내림차순)가 재현 가능하다.
  - 새 회차 **취소(R-10)**: 새 회차만 `CANCELED`가 되고 원 회차 결과·벌칙·규칙은 그대로 유효하다. 원 회차는 다시 돌릴 수 있어야 하므로 취소 회차의 `rerunOf`는 비우고 `canceledRerunOf`에 원 회차를 남긴다(이력 공개 유지).
- **안내 문구 선공개:** 게임 생성 시 입력한 안내 문구(`penaltyNote`)는 결과 공개 전부터 모든 참가자에게 보인다. 벌칙자를 안 뒤 정하는 금액 조건은 설정자·시각과 함께 노출한다(분쟁 대응, 9장).

| (생성) → `WAITING` | 게임 생성(R-0), 또는 다시 돌리기 요청(R-5) | 생성: 그룹 멤버 누구나(생성자 = 진행자). 다시 돌리기: 원 회차 진행자 또는 호스트(E3) |
| `WAITING → PLAYING` | 진행자 또는 호스트가 시작(전원 준비) | **진행자 또는 호스트**(5차 M-A). 서버가 결과(사다리 연결·카드 배열) 생성. 준비 안 한 참가자가 있으면 409(`GAME_NOT_READY`) |
| `PLAYING → REVEALED` | 결과 공개 — 꽝뽑기: 전원 선택 또는 제한 시간 후 자동 배정(R-8, 서버 처리), 사다리: 진행자 또는 호스트의 공개 요청 | 사다리 공개 요청 권한 = **진행자 또는 호스트**(5차 M-A). `revealedAt` 기록, 첫 공개면 `applyOrderAt` 기록, `penaltyKind ≠ NONE`이면 `Penalty` 생성. 금액형이면 금액 영향 변경(정산 직렬화·`REOPENED`) |
| `REVEALED → CLOSED` | **진행자 또는 호스트가 "게임 종료"** | 게임 방(로비) 닫힘 — 이후 참가자 입장·선택 이벤트 없음. 결과·벌칙은 그대로, 금액 영향 없음(`REOPENED` 유발 안 함). 종료하지 않아도 정산·다시 돌리기에 지장 없음 |
| `WAITING`/`PLAYING` → `CANCELED` | 진행자 또는 호스트가 취소(R-10) | 종단 상태. 다시 돌린 회차 취소 시 `rerunOf` 비우고 `canceledRerunOf` 기록 |

- `REVEALED`·`CLOSED`에서 가능한 것: R-9 조건 설정·변경·해제·면제·면제 취소(둘 다 허용), 다시 돌리기(비무효 최신 회차일 때). `WAITING`/`PLAYING`/`CANCELED`에서는 둘 다 409.
- `CLOSED`·`CANCELED`는 다른 상태로 돌아가지 않는다. 다시 돌린 원 회차의 상태는 바뀌지 않는다(`REVEALED`/`CLOSED` 유지). 원 회차 결과가 무효가 됐는지는 후속 회차가 공개됐는지(원 회차 `Penalty.status = VOIDED`)로 판단한다.
- 모든 전이는 `GameSession.version` 낙관적 락. 권한 위반(시작·사다리 공개·종료·취소·다시 돌리기를 진행자도 호스트도 아닌 멤버가 요청)은 403(`NOT_GAME_OPERATOR`), 허용되지 않은 전이는 409.
- **전이 에러 코드(5차 M-A, 모두 409):** `GAME_INVALID_TRANSITION`(현재 상태에서 허용되지 않은 전이 — 예: `REVEALED`가 아닌데 종료, `WAITING`이 아닌데 시작, `PLAYING`이 아닌데 공개), `GAME_NOT_READY`(준비 안 한 참가자가 있는데 시작), `SLOT_ALREADY_PICKED`(꽝뽑기에서 이미 선택된 카드), 취소 불가는 기존 `GAME_NOT_CANCELABLE`, 다시 돌리기 불가는 기존 `GAME_NOT_RERUNNABLE`.

**벌칙 정산 규칙 (고정 금액 + 비율 둘 다 지원)**

| 유형 | 의미 | 예시 |
|---|---|---|
| `FIXED_AMOUNT` | 정해진 금액을 벌칙자가 부담 | "꽝 걸린 사람 2만원 부담" |
| `RATIO` | 대상 금액의 N%를 벌칙자가 부담 | "꼴찌가 2차 30% 부담" |
| `FULL` | 대상 금액 전부 부담 (`RATIO 100%`의 단축 프리셋, **올림 없이** 대상 금액 그대로) | "꼴찌가 2차 쏘기" |

- **조건 설정 시점(R-9):** 게임은 벌칙자만 정한다. 금액 조건(`PenaltyRule`)은 **게임 결과 공개 후(`REVEALED`·`CLOSED`), 지출이 등록된 뒤** 호스트가 게임 단위로 설정하며, 그 게임의 비무효 벌칙자 전원에게 적용된다. 게임당 규칙은 1개(`PenaltyRule.gameSession` 유니크, 오픈 이슈 12). 정산 확정 전이든 후든 변경·해제 가능(확정 후면 정산 `REOPENED`, 아래 "정산 확정 후 수정").
- **대상 = 항상 지출 1건(D1, 오픈 이슈 11 종결):** `PenaltyRule.targetExpense`(필수)는 **같은 모임에 이미 등록된 지출 1건**이다. 차수 전체·여러 지출 합산은 대상으로 고를 수 없다 — 차수에 지출이 여러 건이면 그중 한 건을 고른다(예: 2차 "볼링" 지출). 기존 `targetRound`(차수 대상)는 폐지했고, 그에 따라 "차수 지출 0건이면 0원" 규칙과 차수/지출 대상 겹침 문제도 사라졌다. 이하 "대상 금액" = 대상 지출 금액, "대상 잔액" = 그 지출에서 앞선 벌칙을 뺀 남은 금액.
- **같은 지출에 여러 게임의 규칙:** 아래 적용 순서(N2) — 게임 순번 `applyOrderAt` 순 — 대로 그 지출의 잔액에서 차감한다.
- **벌칙자 여러 명 = 각자 적용(N1):** 한 규칙에 벌칙자가 여럿이면 **각자** 같은 조건을 부담한다(예: `RATIO 30%`, 벌칙자 2명 → 각자 30%). 같은 규칙의 벌칙자끼리는 **순서로 갈리지 않는다** — 잔액이 모자라면 균등 분할(D3, 아래 상한).
- **나머지 분배:** 벌칙자 부담분을 먼저 떼고, 대상 지출의 남은 금액은 **벌칙자를 뺀** 그 지출의 분배 대상자(차수 참석자, 개별 조정 반영)끼리 기본 분배 규칙대로 나눈다(오픈 이슈 2). 여기서 벌칙자 = 그 지출에 `APPLIED` 벌칙이 있는 멤버(`ASSIGNED`·`WAIVED`·`VOIDED` 벌칙자는 일반 참석자로 분배). 같은 차수의 다른 지출은 벌칙과 무관하게 평소대로 분배한다.
- **상한:** 각 벌칙 부담액은 **그 시점 대상 잔액**을 넘을 수 없다 → 같은 지출의 벌칙 합계 ≤ 지출 금액(그 지출에서 남이 돈을 받는 일은 없음). 고정 금액이 잔액보다 크면 잔액까지만, `RATIO`도 100원 올림값이 잔액을 넘으면 잔액까지만 부담한다(아래 S-8).
- **같은 규칙 벌칙자 균등 분할(D3):** 규칙 하나를 적용할 때, 벌칙자 k명 각자의 계산값 v(`RATIO` 100원 올림값 / `FIXED_AMOUNT` 금액 / `FULL` = 그 시점 잔액)의 합 `k × v`가 **그 시점 대상 잔액 R 이하면 각자 v**, 넘으면 **R을 k명이 균등 분할**한다 — 1인 = `ceil(R ÷ k)`를 100원 단위 올림, 올림으로 더 걷힌 `1인 × k − R`은 벌칙자 몫에서 차감해 합계를 정확히 R로 맞춘다(S-8과 같은 방식, 차감 순서는 아래 S-8).
- **경고 규칙:** 같은 대상 지출의 `APPLIED` 벌칙들의 **올림 전 원래 계산값** 합이 대상 금액을 넘으면 정산 확정 전에 경고한다(벌칙이 1개여도 적용). 경고만 하고 확정은 호스트가 확인하면 진행된다.
  - 원래 계산값: `FIXED_AMOUNT` = 고정 금액, `RATIO` = 대상 금액 × pct ÷ 100(올림 전), `FULL` = 대상 금액.
  - **같은 규칙 균등 분할만으로 생기는 초과는 제외(4차 m4):** 규칙 하나의 기여분 = `min(k × v_raw, max(v_raw, T))`(k = 그 규칙의 비무효 `APPLIED` 벌칙자 수, T = 대상 금액).
    - `v_raw` = 1인 **올림 전 원래 계산값**(위 "원래 계산값" 정의) — D3의 v(100원 올림값·그 시점 잔액 기준)와 다르다(5차 m1).
    - 즉 1인 값 자체가 T를 넘으면 그대로(예 3 경고 유지), 1인 값은 T 이하인데 인원수 때문에 넘는 부분은 T에서 자른다(예: `FULL` 2명 "둘이 같이 쏘기" → 기여분 T, 단독이면 경고 없음 — D3로 균등 분할).
  - 정수 비교식(`long`, 모든 값 × 100 스케일): v₁₀₀ = `v_raw × 100` = `고정 금액 × 100` / `대상 금액 × pct` / `대상 금액 × 100`(FULL), T₁₀₀ = `대상 금액 × 100`. `Σ_규칙 min(k × v₁₀₀, max(v₁₀₀, T₁₀₀)) > T₁₀₀`이면 경고(곱셈은 `Math.multiplyExact`).
  - 100원 올림 때문에만 잔액 상한이 걸린 경우는 경고 대상이 아니다(예 4-b). 여러 규칙의 합이 대상 금액을 넘으면 경고가 뜨고, 같은 규칙 벌칙자끼리는 잔액을 균등 분할한다(D3, 예 5-b). (기존 "`FULL`이나 고비율 규칙에 벌칙자가 여러 명이면 경고"는 m4로 대체 — 그 규칙 하나만 있으면 경고 없음)
- **적용 순서(N2):** 같은 대상 지출에 규칙이 여러 개면 아래 정렬 키 순서로 **규칙 단위로 대상 잔액에서 차감**한다. 저장 필드가 아니라 정산 계산 시 정렬 키로 파생한다.
  1. 게임 순번 = `GameSession.applyOrderAt`(그 게임 결과가 처음 공개된 시각, `DATETIME(6)`) 오름차순. **다시 돌린 회차는 원래 회차의 `applyOrderAt`을 이어받아** 원래 순번 위치를 유지한다.
  2. 동시각 타이브레이크 = **원 회차(체인의 첫 회차) `GameSession.id`** 오름차순. 다시 돌린 회차도 원 회차 id로 비교하므로 순번이 바뀌지 않는다.
  3. 같은 규칙의 벌칙자는 순서 없이 함께 처리한다(D3 균등 분할). `Penalty.id`는 균등 분할 시 올림 초과분 차감 순서에만 쓴다(S-8).
- **부담 금액은 파생값(N3):** 벌칙 부담 금액은 저장된 값이 아니라 **정산을 계산할 때마다 새로 계산**한다. 그래서 지출 추가·수정·삭제, 조건 변경, 앞 벌칙의 `VOIDED`가 생기면 다음 계산에 자동 반영된다. **정산 확정·재확정(S-10) 시점에만 그 리비전의 `PenaltyCharge`(`SettlementRevision` 하위)에 스냅샷으로 고정**한다(기존 `Penalty.chargedAmount` 단일 필드는 리비전마다 값이 달라질 수 있어 제거).
- **대상 지출 삭제:** `targetExpense`로 지정된 지출이 삭제되면 같은 트랜잭션에서 그 `PenaltyRule`을 삭제하고(삭제 전 값은 `ChangeLog`에 기록), 해당 게임의 `APPLIED` 벌칙을 `ASSIGNED`(조건 미설정)로 되돌린다. 화면에 "대상 지출이 삭제되어 조건을 다시 입력해야 함"을 표시한다. `PenaltyRule`은 비무효 최신 회차에만 존재하므로(다시 돌린 회차 공개 시 이관) 삭제 대상은 항상 비무효 회차 규칙이고, `VOIDED` 회차를 가리키는 규칙 행이 남아 지출 FK 삭제를 막는 일은 없다. 지난 규칙 이력은 `ChangeLog`로 본다.
- **무효 벌칙:** "다시 돌리기"로 `VOIDED`가 된 벌칙은 정산 계산·벌칙 반영 내역(S-4)에서 제외하고 이력에서만 보인다. `VOIDED`는 종단 상태다(다시 `ASSIGNED`/`APPLIED`/`WAIVED`가 되지 않음). `VOIDED` 전이는 다시 돌린 새 회차의 **결과 공개 시점**에 일어난다(4.4 다시 돌리기 처리 시점).
- **금액 입력 상한:** 지출 금액·`FIXED_AMOUNT` 금액은 1 이상 **1억 원 이하** 정수(`@Min(1)`·`@Max(100_000_000)`, 위반 400). 금액 곱셈(`금액 × pct`, `금액 × 100` 등)은 `Math.multiplyExact`로 해 오버플로를 조용히 넘기지 않는다(상한 1억 × 100 = 10^10이라 `long` 범위 안이므로 실제로는 발생하지 않는 방어 장치).
- **정산 확정 후 수정(D2, 기존 N4 차단 방침 대체, 오픈 이슈 9·10 종결):** 확정 후에도 수정은 막지 않는다. 아래 **금액 영향 변경**이 `CONFIRMED` 정산에서 일어나면 같은 트랜잭션에서 `Settlement`가 `REOPENED`(재확정 필요)가 되고 `ChangeLog`가 남는다. 호스트가 S-10으로 다시 확정해야 하며, 그때 조건 미설정·진행 중 금액형 게임·경고 확인 검사를 다시 거친다.
  - 금액 영향 변경: 지출 추가·수정·삭제, `ExpenseShare`/개별 조정(S-3), 지출이 1건 이상 있는 차수의 참석 변경, 벌칙 조건 설정·변경·해제(R-9), 면제·면제 취소, 다시 돌리기 요청(금액형), 금액형 게임 결과 공개(다시 돌린 회차 포함).
  - 판단은 **변경 종류 기준**이다(계산 결과가 실제로 바뀌었는지 비교하지 않음 — 단순·예측 가능). 결과가 같아도 재확정하면 1인당 변동액이 전원 0원으로 끝난다.
  - 비영향 변경: 행동형·`NONE` 게임의 공개·다시 돌리기, 게임 취소(R-10), 게임 종료(`REVEALED → CLOSED`), 지출 없는 차수의 참석 응답, 장소 관련 변경.
  - 단, **금액형 게임 취소**는 금액 비영향(`REOPENED` 유발 안 함)이지만 S-10의 진행 중 금액형 게임 검사와 경합하지 않도록 Settlement 직렬화 대상에 포함한다(6장 락 표, 5차 m7).
  - 정산을 잠그지 않는다(MVP 단순화. 송금은 앱 밖이라(E1) "송금 완료" 시점을 앱이 모름, 잠금 시점은 오픈 이슈 14).

**정산 상태 전이 (`Settlement.status`, D2)**

| 전이 | 트리거 | 비고 |
|---|---|---|
| (생성) → `DRAFT` | 모임 생성(M-1) | 모임당 1건 |
| `DRAFT → CONFIRMED` | 호스트 확정(S-10) | `SettlementRevision` 1번 생성, `firstConfirmedAt` 기록 |
| `CONFIRMED → REOPENED` | 금액 영향 변경(위 목록) | 변경과 같은 트랜잭션. 행위자는 호스트가 아닐 수도 있음(예: 결과 공개, 참석 변경) |
| `REOPENED → REOPENED` | 추가 금액 영향 변경 | 상태 유지, `ChangeLog`만 추가 |
| `REOPENED → CONFIRMED` | 호스트 재확정(S-10) | 리비전 +1, 새 리비전 전체 송금 안내 + 이전 리비전 대비 1인당 변동액 |
| `DRAFT`에서의 변경 | 금액 영향 변경 | 상태 유지(확정 전이라 재확정 개념 없음) |

- `CONFIRMED`에서 확정을 다시 요청하면 409(`SETTLEMENT_ALREADY_CONFIRMED`). `REOPENED → DRAFT` 같은 "확정 해제"는 없다.
- `REOPENED` 동안 정산 탭의 송금 안내는 마지막 확정 리비전 기준으로 "재확정 필요" 표시와 함께 보인다(송금은 앱 밖이라 막을 대상이 없음, E1).
- **송금 안내 기준 리비전 표시(5차 m5):** 정산 조회 응답에 `basisRevisionNo`(송금 안내의 기준 리비전 번호)를 넣고 화면에 "리비전 n 기준" 라벨을 표시한다. `CONFIRMED`·`REOPENED` = `currentRevisionNo`(마지막 확정 리비전) 기준 저장된 `Transfer`, `DRAFT`(미확정) = `basisRevisionNo` null + 현재 계산값으로 만든 송금 안내를 **"미리보기"**로 표시(저장 안 함).

**재확정 & 변동액 안내 규칙 (S-10·S-11, E1 — 기존 "재확정 & 차액 송금 규칙" 대체)**

기존 규칙(완료 송금 고정·조정 잔액 `A`·보류 송금 409·이전 미완료 송금 `supersededAt`·차액/환불 송금·`STALE_TRANSFER_REVISION`)은 **E1로 대체**됐다. 앱은 송금 여부를 모르므로 아래처럼 "새 기준 전체 + 변동분"만 보여준다.
1. 새 리비전의 멤버별 순잔액 `N_new`(받을 돈 +, 낼 돈 −)을 정산 계산 순서대로 새로 계산한다(`RevisionMemberShare.netBalance`).
2. **송금 안내 목록:** `N_new`에 S-5 송금 최소화를 그대로 적용한 **전체** 목록을 새 리비전의 `Transfer`로 저장한다(차액만이 아님). 이전 리비전의 송금 안내는 그 리비전 스냅샷으로 남고 수정·무효화하지 않는다.
3. **1인당 변동액:** `Δ_m = N_new(m) − N_prev(m)`, `N_prev` = **직전 확정 리비전**(`revisionNo − 1`)의 `RevisionMemberShare.netBalance`. 한쪽 리비전에 행이 없는 멤버는 0으로 본다. 정수(원)이고 `ΣΔ = 0`(두 리비전 모두 합 0이므로). 저장하지 않고 두 스냅샷에서 파생한다(재확정 알림 생성 시·이력 조회 시 계산).
4. **표시 형식:** `Δ < 0` = 더 내야 함, `Δ > 0` = 돌려받음(또는 더 받음). 예: "민수 −20,000원 (낼 돈 30,000 → 50,000)", "철수 +6,600원 (받을 돈 76,800 → 83,400)". `Δ = 0`인 멤버는 "변동 없음".
5. **안내 문구(고정):** "이전 정산대로 이미 송금했다면 변동액만 앱 밖에서 더 보내거나 돌려받으세요. 아직 안 보냈다면 새 송금 안내대로 보내면 됩니다." 변동분을 누가 누구에게 보낼지까지 계산해 줄지는 오픈 이슈 18.

**벌칙 상태 전이 (`Penalty.status`)**

| 전이 | 트리거 | 비고 |
|---|---|---|
| (생성) → `ASSIGNED` | 결과 공개, 벌칙자별 1건 (다시 돌린 회차는 원 회차가 미설정이었을 때) | `penaltyKind`가 `MONEY`·`ACTION`일 때만 생성(`NONE`은 미생성) |
| (생성) → `APPLIED` | 다시 돌린 회차 결과 공개, 원 회차에 `PenaltyRule`이 있었음 | 금액형만. 규칙을 새 회차로 이관하고 같은 트랜잭션에서 생성 |
| (생성) → `WAIVED` | 다시 돌린 회차 결과 공개, 원 회차가 면제 상태였음 | 금액형만. `waivedBy`·`waivedAt`은 원 회차 값 상속 |
| `ASSIGNED → APPLIED` | 호스트가 조건 설정(R-9) | 금액형만. 게임의 비무효 벌칙 전원 동시 전이 |
| `ASSIGNED → WAIVED` | 호스트가 "금액 벌칙 없음" 선택(R-9, S-10) | 금액형만. **게임의 비무효 벌칙 전원 동시** 전이, `waivedBy`·`waivedAt` 기록. 정산 미반영 |
| `APPLIED → ASSIGNED` | 호스트가 조건 해제, 또는 대상 지출 삭제 | `PenaltyRule` 삭제와 같은 트랜잭션 |
| `WAIVED → ASSIGNED` | 호스트가 면제 취소 | **게임의 비무효 벌칙 전원 동시**, `waivedBy`·`waivedAt` 비움(이력은 `ChangeLog`). 정산 확정 후에도 가능(정산 `REOPENED`) |
| `APPLIED → WAIVED` | 호스트가 `APPLIED` 게임에서 "금액 벌칙 없음" 선택(E2, 4차 M6) | 한 트랜잭션에서 `PenaltyRule` 삭제 + 전원 `WAIVED`(`waivedBy`·`waivedAt` 기록). `ChangeLog` 2건(규칙 해제, 면제) |
| `WAIVED → APPLIED` | 호스트가 `WAIVED` 게임에서 조건 설정(E2) | 한 트랜잭션에서 면제 취소(`waivedBy`·`waivedAt` 비움) + `PenaltyRule` 생성 + 전원 `APPLIED`. `ChangeLog` 2건(면제 취소, 규칙 설정) |
| `ASSIGNED`/`APPLIED`/`WAIVED` → `VOIDED` | 다시 돌린 새 회차의 결과 공개 | 종단 상태. 다시 돌리기 요청만으로는 전이하지 않음 |

- 상태 의미: `ASSIGNED` = 벌칙자 확정·금액 조건 미설정(행동형은 "행동 벌칙 대상자"), `APPLIED` = 조건 설정 완료·정산 반영, `WAIVED` = 금액 벌칙 없음으로 확정, `VOIDED` = 다시 돌리기로 무효.
- 금액형 벌칙의 모든 전이는 `ChangeLog`에 기록되고, 정산이 `CONFIRMED`면 같은 트랜잭션에서 `REOPENED`로 바꾼다.
- 행동형(`ACTION`) 벌칙은 `ASSIGNED`에 머물며 정산과 무관하다(확정 차단 대상 아님, 정산 확정 후에도 다시 돌리기 가능, `REOPENED` 유발 안 함). 전이는 `ASSIGNED → VOIDED`만 있다.
- 조건 변경(`APPLIED` 상태에서 규칙 값·대상 수정)은 상태 전이 없이 `PenaltyRule`만 갱신되고, 부담액은 다음 계산에서 새로 나온다.

**원 단위 처리 규칙 (S-8)**
- 1인 부담액 = 분배 대상 금액 ÷ 인원 → **100원 단위 올림**.
- 올림으로 더 걷힌 금액(`1인 부담액 × 인원 − 분배 대상 금액`)은 **결제자 몫에서 차감**해 총액을 정확히 맞춘다.
- 벌칙 부담액(모두 `long` 정수 연산, 부동소수점 금지):
  - `FIXED_AMOUNT`: 입력한 정수 금액 그대로, 단 `min(고정 금액, 대상 잔액)`.
  - `RATIO`: 비율 `pct`는 **1~100 정수(%)**. **`min(ceil(대상 금액 × pct / 100 / 100) × 100, 그 시점 대상 잔액)`**. 정수 연산으로는 `(대상 금액 × pct + 9,999) / 10,000 × 100`(정수 나눗셈). 올림 때문에 대상 금액을 넘거나 나머지가 음수가 되는 일을 막는다.
  - `FULL`: 올림 없이 대상 잔액 그대로.
  - **같은 규칙 벌칙자 균등 분할(D3):** 위 계산값 v로 `k × v ≤ R`이면 각자 v. 넘으면 1인 = `(R + 100k − 1) / (100k) × 100`(정수 나눗셈 = `ceil(R ÷ k)`의 100원 올림), 초과분 `E = 1인 × k − R`을 **① 그 지출의 결제자가 벌칙자 중에 있으면 결제자 몫에서 먼저, ② 나머지는 `Penalty.id` 내림차순**으로 각 몫에서 0원 밑으로 내려가지 않게 차감한다. 결과 합계는 정확히 R. 벌칙자가 1명이면 이 규칙은 기존 `min(v, R)`과 같다(예 3).

**정산 계산 순서**
1. 지출 항목별 금액(벌칙 대상은 항상 지출 1건)
2. `APPLIED` 벌칙 부담분 차감 — 지출마다 그 지출을 대상으로 한 규칙을 정렬 키 `(applyOrderAt, 원 회차 GameSession.id)` 순으로 적용, 규칙마다 잔액 상한·같은 규칙 균등 분할(D3) 적용. `ASSIGNED`·`WAIVED`·`VOIDED` 제외. 확정 전에는 매번 새로 계산, 확정·재확정 시 리비전 스냅샷(`PenaltyCharge`)
3. 지출별 남은 금액을 그 지출의 벌칙자 제외 분배 대상자에게 기본 분배(가중치/제외 반영)
4. 결제자별 받을 돈 − 낼 돈 = 순잔액
5. 송금 최소화 알고리즘으로 송금 안내 목록 생성(재확정이어도 새 순잔액 전체 기준. 이전 확정 리비전 대비 1인당 변동액은 별도 계산 — 재확정 & 변동액 안내 규칙)

| S-4 | Given 민수에게 2차 지출 "볼링" 대상 `RATIO 30%` 벌칙이 `APPLIED` / When 정산 탭을 조회하면 / Then "민수: 사다리 꽝 → 2차 볼링 +30,000원" 형식으로 벌칙 출처(게임)·대상 지출·금액·조건 설정자·설정 시각이 항목별로 노출된다. `ASSIGNED` 벌칙은 금액 없이 "조건 미설정", `WAIVED`는 "금액 벌칙 없음"과 면제자·면제 시각(`waivedBy`·`waivedAt`)으로 표시되고, `VOIDED`는 이력에서만 보인다. |

Given `REOPENED` 정산 / When 호스트가 재확정하면 / Then 같은 검사(미설정·진행 중 금액형 게임·경고 확인)를 다시 거쳐 리비전 +1이 저장되고, 송금 안내는 새 순잔액 **전체** 기준으로 생성되며 이전 리비전 `Transfer`는 바뀌지 않는다(예 6). `CONFIRMED` 상태에서 다시 요청하면 409(`SETTLEMENT_ALREADY_CONFIRMED`). |
| S-11 | Given 리비전 1로 확정된 정산 / When 멤버가 지출 금액을 수정하면 / Then 수정은 성공하고 같은 트랜잭션에서 `Settlement`가 `REOPENED`, `ChangeLog`에 (행위자, 시각, `Expense`, `UPDATE`, 전/후 JSON)이 저장되며, 커밋 후 모임 구독자에게 "정산 재확정 필요" 이벤트가 브로드캐스트된다. Given 예 6 조건 / When 재확정하면 / Then 리비전 2 송금 안내는 민수→철수 50,000, 영희→철수 16,700, 지수→철수 16,700(3건, 합 83,400원)이고, 리비전 1 대비 1인당 변동액은 철수 +6,600 / 민수 −20,000 / 영희 +6,700 / 지수 +6,700(합 0)으로 반환되며, 리비전 1의 송금 안내 3건은 그대로 남는다. 그리고 변동액이 0이 아닌 멤버 목록·변동액과 "이미 송금했다면 변동분만 앱 밖에서 주고받으세요" 안내가 "정산 재확정" 이벤트로 브로드캐스트되고 카톡 공유 문구가 생성된다. When 리비전 목록·변경 로그를 조회하면 / Then 그룹 멤버는 리비전별 확정자·시각·부담액·순잔액·직전 대비 변동액·송금 안내와 `ChangeLog` 항목을 시간순으로 볼 수 있고, 비멤버는 403(`NOT_GROUP_MEMBER`). |

## 5. 화면 구성 (모바일 우선)

1. **그룹 홈** — 다가오는 모임, 지난 모임, 명예의 전당 요약
2. **모임 상세** — 탭: `장소` / `참석` / `게임` / `정산`
   - 장소 탭: 차수별 장소 카드(확정 장소 label + 카카오맵 지도·길찾기 링크, 직접 입력 장소는 사용자 지도 링크 또는 카카오맵 검색 링크), 투표 중이면 후보 목록·득표 현황·후보 추가(장소 검색)
   - 참석 탭: 차수별 응답 현황판, 내 응답 버튼
   - 게임 탭: 사다리 / 꽝뽑기 / 룰렛 / 볼링 점수 카드, 결과 로그(다시 돌리기·취소 이력 포함), 게임별 벌칙자·벌칙 상태(조건 미설정 / 적용 / 면제), 게임 시작(`WAITING`, 전원 준비 시 활성)·사다리 결과 공개(`PLAYING`)·진행 중 게임 취소·결과 공개 게임의 다시 돌리기·게임 종료(진행자·호스트에게만 버튼 노출, E3·5차 M-A)
   - 정산 탭: 지출 목록 → **벌칙 조건 입력(호스트, 조건 미설정 게임 목록 + 고정/비율/전액 프리셋 + 대상 지출 1건 선택(차수별 지출 목록) + "금액 벌칙 없음", 적용·면제 게임도 서로 전환 가능(E2))** → 1인당 금액 → 경고·확정 → **송금 안내 목록**("누가 누구에게 얼마" + 카톡 공유 문구, 송금은 앱 밖 — E1. 딥링크·계좌 복사는 S-7(P1))
     - 송금 안내 상단에 **"리비전 n 기준"** 라벨(`basisRevisionNo`). `REOPENED`면 마지막 확정 리비전 기준 + "재확정 필요", `DRAFT`면 라벨 대신 **"미리보기"**(확정 전 계산값, 5차 m5)
     - 확정 후 금액 영향 변경 시 상단에 **"재확정 필요" 배너**(무엇이 바뀌었는지 `ChangeLog` 요약) + 호스트 재확정 버튼
     - 재확정 직후 **변동액 카드**: 이전 확정 리비전 대비 1인당 변동액("민수 −20,000원 (낼 돈 30,000 → 50,000)") + 고정 안내 문구("이미 송금했다면 변동분만 앱 밖에서 더 보내거나 돌려받으세요"), 그 아래 새 리비전 전체 송금 안내 목록
     - **정산 이력**: 리비전 목록(번호·확정자·시각·멤버별 부담액·순잔액·직전 리비전 대비 변동액) + 리비전별 송금 안내(읽기 전용 기록) + 변경 로그(누가·언제·무엇을·전→후)
3. **게임 실행 화면** — 풀스크린, 한 폰을 돌려가며 써도 되는 큰 UI. 게임 생성 시 벌칙 종류·안내 문구 입력
4. **초대 진입 화면** — 링크 접속 시 "OO 모임에 초대받았어요" + 카카오 로그인 버튼 하나 → 로그인 후 바로 참석 응답 화면

## 6. 비기능 요구사항

| 영역 | 요구사항 |
|---|---|
| 플랫폼 | **모바일 웹 우선 + PWA**(홈 화면 추가, 웹 푸시). 앱 설치 강요 안 함 |
| 공유 | **카카오톡 공유**(OG 태그 미리보기: "토요일 모임 · 강남 OO식당 · 5/8명 참석") — 바이럴 핵심 경로 |
| 구조 | **SPA + REST API.** Spring Boot는 JSON API와 WebSocket만 맡고, 화면은 별도 SPA(React 계열)가 담당. OG 태그는 SPA가 못 만들어주니까 초대/모임 링크 경로는 서버에서 OG 메타만 담은 HTML을 내려준다 |
| 인증 | **카카오 로그인(OAuth2).** 백엔드가 카카오 인가 코드를 받아 회원 조회/생성 후 자체 토큰(Access + Refresh, `HttpOnly` 쿠키) 발급. 카카오톡 인앱 브라우저에서 로그인이 깨지지 않는지 꼭 확인 |
| 인가 | 초대 링크로 들어온 사람은 로그인 직후 원래 링크로 돌아가 그룹에 자동 가입. 그룹 리소스는 그룹 멤버만 접근. 금융 정보(계좌)는 그룹 멤버에게만 노출. 벌칙 조건 설정·면제·면제 취소·정산 확정·재확정은 호스트만(403 `NOT_MEETING_HOST`). **호스트 = `Meeting.hostMemberId`(모임 생성자, D4)**. 게임 시작(R-0)·사다리 결과 공개(R-1)·게임 취소(R-10)·다시 돌리기(R-5)·게임 종료(`REVEALED → CLOSED`)는 진행자(`GameSession.createdBy`) 또는 호스트(그 외 403 `NOT_GAME_OPERATOR`, E3·5차 M-A). 꽝뽑기 카드 선택은 참가자 본인. 비멤버의 그룹 리소스 접근은 403 `NOT_GROUP_MEMBER`. 정산 리비전·변경 로그는 그룹 멤버 조회 가능 |
| 실시간 | **MVP부터 WebSocket(STOMP)** — 게임 방(로비/진행/공개)은 필수. 참석 현황·장소 투표 현황·정산 현황(벌칙 조건 설정, `REOPENED` 전이, 재확정 결과 포함) 갱신도 같은 채널 사용. **브로드캐스트는 트랜잭션 커밋 후에만**(`@TransactionalEventListener(phase = AFTER_COMMIT)`) 보내 롤백된 상태가 클라이언트에 나가지 않게 한다. 끊겼다 다시 붙으면 REST로 현재 상태를 받아 복구 |
| 알림(재확정) | 정산이 `REOPENED`가 되면 모임 구독자에게 "재확정 필요" 이벤트(호스트 화면엔 재확정 버튼 강조). 재확정되면 "정산이 바뀌었어요(리비전 n)" 이벤트와 함께 **이전 확정 리비전 대비 1인당 변동액(0이 아닌 멤버 목록)**과 새 송금 안내 목록을 보내고, 호스트용 카톡 공유 문구("정산이 수정됐어요(리비전 2): 민수 −20,000원, 철수 +6,600원, 영희 +6,700원, 지수 +6,700원. 이미 송금했다면 변동분만 주고받으세요 …")를 생성한다(E1 — 송금 확인 요청 알림은 없음, 웹 푸시는 기존 범위대로 P1) |
| 외부 API | **카카오 로컬(장소 검색)** — 서버가 매 요청마다 실시간 프록시 호출, **검색 결과 캐싱·저장 금지**(응답 본문을 DB·캐시에 남기지 않음, 저장은 `kakaoPlaceId`만 — 4.3 장소 도메인 규칙), 서버 측 호출량 제한, 일일 쿼터 초과 시 직접 입력(P-1)으로 폴백. 지도·길찾기는 카카오맵 URL 링크로 대체(직접 입력 장소는 `manualMapUrl`(https, ≤2,048자) 또는 `/link/search/` 링크) |
| 금액 처리 | 금액은 정수(원, `long`) 처리, 부동소수점 금지. 비율은 1~100 정수 %, `ceil(금액 × pct / 100 / 100) × 100`을 `(금액 × pct + 9,999) / 10,000 × 100` 정수 연산으로 계산 후 대상 잔액 상한, `FULL`은 올림 없음, 같은 규칙 벌칙자는 잔액 초과 시 균등 분할(S-8). 지출·고정 금액 1~1억 원(`@Max(100_000_000)`), 곱셈은 `Math.multiplyExact`. 벌칙 부담액은 파생값이며 정산 확정·재확정 시 리비전 스냅샷. **정산 확정 후 수정은 허용하고 이력을 남긴다** — 확정마다 `SettlementRevision` 스냅샷, 변경마다 `ChangeLog`(전/후 JSON), 정산은 `REOPENED` 후 재확정(4.5 정산 확정 후 수정, 7장 설계 메모) |
| 트랜잭션·동시성 | 정산/게임 결과 저장은 트랜잭션 처리, 동시 응답 충돌 시 낙관적 락 (아래 표). 사용자 행동이 몰리는 쓰기(참석 응답, 게임 결과 공개·자동 배정)는 락 충돌 시 서버에서 최대 2회 재시도 후 409(`CONCURRENT_MODIFICATION`). 꽝뽑기 카드 선택은 `PESSIMISTIC_WRITE`로 직렬화하므로 재시도 대상에서 제외(5차 m2). **재시도 규칙(4차 m7):** ① `@Transactional` Service **바깥의 facade**에서 재시도(매 시도가 새 트랜잭션), ② 대상 예외는 `ObjectOptimisticLockingFailureException`만(유니크 위반 `DataIntegrityViolationException`·`BusinessException`은 재시도 안 함 — 예: 같은 카드 선택은 바로 409 `SLOT_ALREADY_PICKED`), ③ 재시도 시 상태를 다시 읽어 이미 목표 상태면(이미 `REVEALED`, 같은 응답 저장됨 등) 쓰기 없이 현재 상태로 성공 응답(멱등). 송금 체크는 E1로 폐지돼 대상에서 제외 |

**아키텍처 방침 (CLAUDE.md 반영)**
- Spring Boot 4.1 + Java 21, Gradle 9, MySQL, Spring Data JPA.
- 레이어드 아키텍처: **Controller → Service → Repository**. 계층 간 전달은 **DTO**, 엔티티를 API 응답으로 직접 노출하지 않음.
- 생성자 주입(`@RequiredArgsConstructor`), 트랜잭션 경계는 **Service 계층 `@Transactional`**.
- **일관된 API 응답·예외 구조:** 모든 REST 응답은 공통 래퍼(예: `{ success, data, error: { code, message } }`)로 통일하고, `@RestControllerAdvice`가 `BusinessException(ErrorCode)`·검증 실패·락 충돌·유니크 위반을 공통 에러 응답으로 변환한다.
- 정산 계산은 JPA·Spring에 의존하지 않는 **순수 도메인 로직**으로 분리해 단위 테스트를 촘촘히 붙인다. 입력(지출, 참석, `APPLIED` 벌칙 + 정렬 키, 규칙) → 출력(멤버별 부담액·순잔액, 벌칙별 부담액, 경고, 송금 안내 목록)의 순수 함수로 두고, 확정·재확정 시 그 출력을 `SettlementRevision` 스냅샷으로 저장한다. 재확정 변동액은 두 리비전의 `RevisionMemberShare.netBalance`를 받아 `Δ`를 내는 별도 순수 함수(입력 순잔액 맵 2개 → 출력 멤버별 Δ, 합 0 검증)로 둔다(E1로 완료 송금 입력·조정 잔액 `A` 제거).

| 대상 | 충돌 상황 | 전략 |
|---|---|---|
| 참석 응답 (M-3) | 같은 멤버 중복 응답 | `(round, member)` 유니크 제약 + upsert. 지출이 있는 차수면 아래 정산 직렬화 대상 |
| 그룹 가입 (G-3) | 같은 링크 동시 클릭 | `(group, member)` 유니크 제약 |
| 장소 투표 (P-3) | 중복 투표 | `(candidate, member)` 유니크 제약 |
| 장소 확정 (P-4) | 자동 마감 vs 수동 확정 | `Round.version` 낙관적 락, 늦은 쪽 409 |
| 꽝뽑기 선택 (R-2) | 같은 카드 동시 선택, 여러 참가자 동시 선택 | `GameSession` 행 **`PESSIMISTIC_WRITE`**(`@Lock`, 행 잠금 대기)로 선택 요청 직렬화 → 잠금 획득 후 슬롯 점유 검사, 같은 카드 충돌은 `(gameSession, pickedSlot)` 유니크 제약으로 최종 차단 → 늦은 쪽 409(`SLOT_ALREADY_PICKED`), 재시도 안 함(5차 m2, 기존 "`GameSession.version` 낙관적 락" 대체 — 서로 다른 카드 동시 선택이 낙관적 락 충돌로 실패하는 문제 제거) |
| 게임 상태 전이 (R-0/R-8/R-10, 게임 종료) | 시작·공개·자동 배정·취소·종료(`REVEALED → CLOSED`) 경합 | `GameSession.version` 낙관적 락. 단 **꽝뽑기 R-8 자동 배정**은 카드 선택(R-2)과 같은 `GameSession` 행 `PESSIMISTIC_WRITE`를 잡아 마지막 카드 선택과 직렬화한다 — 잠금 획득 후 아직 `PLAYING`이고 미선택 참가자가 있을 때만 배정·공개, 이미 `REVEALED`면 쓰기 없이 종료(멱등) |

| 다시 돌리기 (R-5) | 같은 회차에 동시 요청 → 새 회차 2개 생성 위험 | 사전 검사(원 회차 `REVEALED`/`CLOSED`·후속 회차 없음, 아니면 409 `GAME_NOT_RERUNNABLE`) + `GameSession.rerunOf` **유니크 제약**(NULL 허용, 회차당 후속 회차 1개, 취소 시 `rerunOf` 비움)으로 충분 — 늦은 쪽은 유니크 위반 409(`RERUN_ALREADY_EXISTS`), 또는 먼저 온 요청이 이미 커밋됐으면 사전 검사에서 409(`GAME_NOT_RERUNNABLE`) — 둘 중 하나의 409(5차 m3). 요청 트랜잭션은 원 회차 행을 수정하지 않으므로 원 회차에 별도 락(`OPTIMISTIC_FORCE_INCREMENT`)을 잡지 않는다(4차 m5, 기존 "원 `GameSession.version` 낙관적 락" 표기 대체 — 원 회차를 읽기만 하면 version 검사가 일어나지 않아 의미가 없었음). 원 회차 `Penalty → VOIDED`·규칙 이관·새 벌칙 생성은 **새 회차 결과 공개** 트랜잭션에서 처리 |
| 벌칙 조건 설정·면제·해제 (R-9) | 조건 설정 vs 새 회차 결과 공개(원 회차 `→VOIDED`·규칙 이관), 조건 설정 vs 대상 지출 삭제(`APPLIED→ASSIGNED`), 적용 ↔ 면제 직접 전환(E2), 호스트 동시 수정 | `PenaltyRule.gameSession` 유니크 제약 + `Penalty.version`·`PenaltyRule.version` 낙관적 락, 늦은 쪽 409. `VOIDED`는 종단 상태라 늦게 도착한 조건 설정은 409. `APPLIED ↔ WAIVED` 전환은 규칙 삭제/생성과 벌칙 전원 전이를 한 트랜잭션에서 처리 |
| **정산 직렬화** (S-10/S-11) vs 금액 영향 변경 | 확정 검사(미설정 0건·진행 중 금액형 게임 0건) 직후 변경이 끼어듦 | 아래 쓰기가 모두 같은 모임 `Settlement` 행을 `OPTIMISTIC_FORCE_INCREMENT`로 잡아 직렬화: **확정·재확정**, 지출 추가/수정/삭제, `ExpenseShare`·개별 조정, 지출 있는 차수의 참석 변경, 조건 설정/변경/해제·면제·면제 취소(적용 ↔ 면제 전환 포함), 다시 돌리기 요청(금액형), 금액형 결과 공개, 금액형 게임 취소(금액 비영향이지만 S-10 진행 중 금액형 게임 검사와 경합하지 않도록 포함, 5차 m7). 늦은 쪽 409. `CONFIRMED` 상태에서 들어온 금액 영향 쓰기는 거부하지 않고 같은 트랜잭션에서 `REOPENED`로 전이. (송금 체크는 E1로 폐지돼 대상에서 제거) |
| 금액형 게임 생성·시작 | 확정 검사 직후 새 금액형 게임이 생성·시작됨 | **의도적으로 직렬화 밖**(4차 m6): 생성·시작은 `Penalty`를 만들지 않아 금액에 영향이 없고, 금액 영향은 결과 공개 시점에 생기며 그 공개는 직렬화 대상이라 확정 후라면 `REOPENED`로 이어진다 |
| 변경 로그 (S-11) | 쓰기와 로그 불일치 | `ChangeLog`는 변경과 **같은 트랜잭션**에서 insert(append-only, 수정·삭제 API 없음) |

**설계 메모**
- 그룹 안에서의 닉네임은 `GroupMember`에 따로 둔다(그룹마다 다른 별명 가능).
- 호스트가 투표 없이 바로 장소를 정해도 후보 1개짜리로 `PlaceCandidate`를 만들고 `CONFIRMED` 처리한다(확정 장소 조회 경로를 하나로 통일). 장소 값은 공통 `Place` **임베디드 값 타입**(`kakaoPlaceId?`, `label`, `manualAddress?`, `manualMapUrl?`)으로 묶어 `PlaceCandidate`·`FavoritePlace`에서 재사용.
- `Place` 저장 규칙(4.3 장소 도메인 규칙, 오픈 이슈 5): 카카오 검색 장소는 `kakaoPlaceId` + 사용자가 확정한 `label`만 저장하고 `manual*`은 null. 직접 입력 장소는 `kakaoPlaceId` null + `label`·`manualAddress`·`manualMapUrl`(사용자 입력, `https`만·≤2,048자, 요청 DTO Bean Validation으로 검증). 주소·좌표·카테고리 등 카카오 응답 필드는 저장하지 않는다. 지도·길찾기 링크는 저장하지 않고 `kakaoPlaceId`(또는 `manualAddress`/`label` 검색어)로 조회 시점에 생성한다.
- 벌칙은 **벌칙자와 금액 조건을 분리**한다. `Penalty`는 결과 공개 시 벌칙자(`member`)별로 생성되는 실제 벌칙(`ASSIGNED`), `PenaltyRule`은 게임 후·지출 등록 뒤 호스트가 게임 단위로 만드는 금액 조건이다(그 게임 비무효 벌칙자 전원에게 각자 적용). 벌칙 종류(금액형/행동형/없음)는 게임 생성 시 `GameSession.penaltyKind`로 정한다. 상태 전이는 4.5 벌칙 상태 전이 표.
- 벌칙 부담액은 **파생값**이다. 확정 전에는 어디에도 저장하지 않고 정산 계산 때마다 새로 계산하며, 정산 확정·재확정(S-10) 시에만 그 리비전의 `PenaltyCharge`로 스냅샷을 남긴다. 기존 `Penalty.chargedAmount` 단일 필드는 리비전마다 값이 달라져 의미가 모호하므로 **제거**한다(최신 값이 필요하면 현재 리비전의 `PenaltyCharge` 조회).
- `PenaltyRule.targetExpense`는 필수 FK(지출 1건)다. 차수 대상(`targetRound`)은 폐지(D1).
- "다시 돌리기"는 새 `GameSession`을 만들고 `rerunOf`로 이전 회차를 가리켜 재실행 이력을 보존한다(`rerunOf` 유니크라 회차당 후속 회차는 1개, 다시 돌리기는 항상 최신 회차에서만). 새 회차는 원 회차의 `applyOrderAt`·`rootSessionId`를 상속하고, `type`·`penaltyKind`·`penaltyNote`·참가자 목록을 복제(변경 불가)하며, `createdBy`는 요청자(원 회차 진행자 또는 호스트, E3)다. 다시 돌리기 가능 조건은 4.4 게임 상태 전이 표. **조건 상태 상속은 새 회차 결과 공개 시점**에 한다 — 원 회차에 `PenaltyRule`이 있으면 새 회차로 **이관**(`gameSession`만 변경, 복제 아님, `setBy`·`updatedAt` 유지)해 새 벌칙자를 바로 `APPLIED`, 면제였으면 `WAIVED`(`waivedBy`·`waivedAt` 상속), 미설정이면 `ASSIGNED`. 원 회차의 `Penalty`는 삭제하지 않고 `VOIDED`로 바꿔 이력을 보존하고, 원 회차의 규칙 이력은 `ChangeLog`(이관 기록)로 본다(기존 "원 회차 `PenaltyRule`도 이력용으로 남김"을 대체 — 지출 삭제 시 FK 문제 해소). 새 회차가 공개 전에 취소(R-10)되면 `rerunOf`를 비우고 `canceledRerunOf`에 원 회차를 남겨, 원 회차는 그대로 유효하고 다시 돌릴 수 있다.
- 적용 순서는 저장 필드(기존 `PenaltyRule.applyOrder`)를 두지 않고 정렬 키 `(GameSession.applyOrderAt, rootSessionId)`로 규칙 순서를 파생한다(4.5 적용 순서). `applyOrderAt`은 `DATETIME(6)`(마이크로초)로 저장하고, 그래도 같으면 `rootSessionId`로 가른다. 같은 규칙 벌칙자는 균등 분할(D3)이며 `Penalty.id`는 초과분 차감 순서에만 쓴다. 결과 공개 시 `Penalty`를 `memberId` 오름차순으로 insert하므로 이 순서는 결정적이다(4차 m3).
- `Meeting.hostMemberId`는 모임 생성자로 고정(D4). 권한 검사는 Service 계층에서 `meeting.isHost(memberId)`로 일원화한다.
- `Settlement`는 모임당 1건으로 모임 생성 시 `DRAFT`로 만든다. 금액에 영향을 주는 쓰기·확정·재확정은 이 행의 `version`을 강제 증가시켜 직렬화한다(6장 락 표, 송금 체크는 E1로 폐지). 상태 전이는 4.5 정산 상태 전이 표.
- **정산 이력 저장(D2, 오픈 이슈 9·10 종결) — 두 가지를 모두 둔다.**
  - `SettlementRevision`: 확정·재확정마다 1건(리비전 번호, 확정자·시각, 경고 확인 여부) + 하위 `RevisionMemberShare`(멤버별 부담액·순잔액), `PenaltyCharge`(벌칙별 부담액), 그 리비전의 `Transfer`(송금 안내). 생성 후 수정하지 않는 스냅샷이다. `Settlement.currentRevisionNo`가 최신 리비전을 가리킨다.
  - **리비전 참조 표기 통일(4차 M2):** 리비전 식별은 모임 안 번호 `revisionNo`(1부터)로만 말하고, `Settlement.currentRevisionNo`가 최신 번호를 갖는다. 하위 엔티티(`RevisionMemberShare`·`PenaltyCharge`·`Transfer`)는 `revision` FK(→ `SettlementRevision`)로 소속된다. `revisionId`라는 표기·`revisionId == currentRevisionNo` 같은 id/번호 혼용 비교는 쓰지 않는다(그 검사를 하던 송금 체크는 E1로 폐지).
  - `PenaltyCharge` 스냅샷 컬럼(4차 m2): 부담액 `amount`와 함께 확정 시점의 `moneyType`·값(`fixedAmount` 또는 `ratioPct`)·`targetExpenseId`·`targetExpenseAmount`(확정 시점 대상 지출 금액)·`targetExpenseMemo`(확정 시점 대상 지출 메모, 5차 m4)를 복사해 둔다. 이후 규칙이 바뀌거나 대상 지출이 삭제돼도 그 리비전에서 "왜 이 금액인지"를 설명할 수 있게 하려는 것이며, `targetExpenseId`는 지출 삭제를 막지 않도록 FK가 아닌 값 컬럼이다.
  - `ChangeLog`: 모임 단위 append-only 로그(누가·언제·대상 엔티티·변경 종류·전/후 JSON·변경 후 정산 상태). 기록 대상: R-9 조건 설정·변경·해제, 면제·면제 취소(적용 ↔ 면제 직접 전환은 2건 — 규칙 해제+면제 / 면제 취소+규칙 설정, E2), `PenaltyRule` 삭제(대상 지출 삭제)·이관(다시 돌리기), **금액형 게임 최초 결과 공개**(벌칙자 `ASSIGNED` 생성, 4차 m1), 다시 돌리기 요청·새 회차 공개(`VOIDED`), 게임 취소, 지출·`ExpenseShare`·개별 조정 추가/수정/삭제는 **항상**, 참석 변경은 **정산이 한 번이라도 확정된 뒤**(리비전 ≥ 1)부터 기록(확정 전 참석 응답은 양이 많고 분쟁 가치가 낮음).
  - `Transfer`는 `revision`에 속한 **송금 안내(계산 결과)**다 — from·to·amount만 있고 송금 상태(`sentAt`·`confirmedAt`·`supersededAt`·`version`)는 없다(E1). 리비전마다 그 리비전 순잔액 전체 기준으로 새로 만들고, 이전 리비전 `Transfer`는 그대로 남는다. 재확정 시 1인당 변동액은 `RevisionMemberShare` 두 리비전 비교로 파생한다(4.5 재확정 & 변동액 안내 규칙).

```
5-a. 지출·정산 계산·최초 확정 + REOPENED 전이 + ChangeLog 공통 헬퍼

     확정 후 지출·조정·참석 변경 시 CONFIRMED → REOPENED, ChangeLog 공통 헬퍼(append-only, 같은 트랜잭션),
     AFTER_COMMIT 브로드캐스트("재확정 필요" 이벤트), 락 충돌 재시도 facade(ObjectOptimisticLockingFailureException만)
6. 게임 방·사다리·꽝뽑기 (penaltyKind·penaltyNote 포함), 게임 상태 전이(REVEALED → CLOSED 종료 포함), 게임 취소(R-10),
   진행자·호스트 권한(NOT_GAME_OPERATOR)
7. 벌칙자 확정: 결과 공개 시 Penalty ASSIGNED(memberId 오름차순 insert), applyOrderAt(DATETIME(6))·rootSessionId 기록,
   금액형 최초 공개 ChangeLog, 다시 돌리기(권한·설정 복제 E3, GAME_NOT_RERUNNABLE 사전 검사, rerunOf 유니크,
   새 회차 공개 시 VOIDED·규칙 이관(setBy·updatedAt 유지)·조건 상태 상속, 취소 시 rerunOf 해제)
8. 정산 연동: 게임 후 조건 설정·면제·면제 취소(R-9, 대상 지출 1건, APPLIED ↔ WAIVED 직접 전환 E2),
   부담액 파생 계산·정렬 키·같은 규칙 균등 분할·경고(m4 보정), 대상 지출 삭제 시 ASSIGNED 복귀(+ChangeLog),
   금액형 벌칙 변경·결과 공개·다시 돌리기 시 REOPENED(5-a 헬퍼 재사용),
   정산 확정 게이트(S-10: 미설정 해소·진행 중 금액형 게임 차단·경고 확인·PenaltyCharge 리비전 스냅샷(조건 스냅샷 컬럼 포함))
5-b. 재확정·리비전 비교·알림
     재확정(REOPENED → CONFIRMED, 리비전 +1, 8단계 확정 게이트 재사용), 새 리비전 전체 송금 안내,
     이전 확정 리비전 대비 1인당 변동액(순수 함수, 합 0 검증), 리비전 목록·ChangeLog 조회 API,
     재확정 알림 이벤트·카톡 공유 문구(변동액 + 고정 안내 문구)
9. 통합 테스트: 예 1~6 시나리오(API → DB → 계산 결과·리비전 스냅샷·변동액 검증)
```

- **5-a / 5-b 경계:** 5-a = 리비전이 **1개**만 있어도 되는 모든 것(지출·계산·최초 확정·`REOPENED` 전이·`ChangeLog` 기록). 5-b = 리비전이 **2개 이상**이어야 의미 있는 것(재확정, 리비전 간 변동액, 이력 조회 화면용 API, 재확정 알림). 5-a 직후엔 `REOPENED`에서 재확정할 수 없는 상태가 생기지만 내부 개발 단계라 허용하고, MVP 배포는 5-b 이후. 5-b를 게임·벌칙(6~8) 뒤에 두는 이유: 재확정 게이트가 8단계의 미설정 벌칙·진행 중 금액형 게임 검사를 그대로 재사용하기 때문(4차 M8).
- **범위 주의(D2, E1):** 확정 후 수정 허용으로 5·8단계 범위가 커졌다(리비전 스냅샷, 변경 로그, 재확정 알림). E1로 송금 상태(보냄·확인·대체)·보류 송금·차액/환불 송금 계산이 빠져 범위가 줄었다 — 재확정 송금 안내는 기존 송금 최소화 함수를 새 순잔액에 그대로 쓰고, 변동액은 순잔액 차의 단순 계산이다. `ChangeLog` 기록은 Service 공통 헬퍼(또는 도메인 이벤트)로 한 곳에서 처리한다(5-a에서 만들고 7·8단계가 재사용).

정산 계산 로직은 순수 도메인 로직으로 분리해서 단위 테스트를 촘촘히 붙인다(돈 문제는 버그 나면 신뢰가 바로 깨짐). 4.5의 계산 예시 6개·8케이스(1, 2, 3, 4-a, 4-b, 5-a, 5-b, 6, 경고 여부 포함)와 S-8 수용 기준의 `FULL` 2명 경고 제외 케이스는 그대로 단위 테스트 케이스로 쓰고(5-a·8·5-b 단계에서 해당 함수와 함께), 9단계에서 같은 예시를 통합 테스트로 다시 돌린다.

| 기존 앱(토스 N빵, 사다리 앱)과 경쟁 | 단일 기능이 아니라 **참석→게임→정산 연결**로 차별화 |
| 계좌 정보 노출 | 그룹 멤버 한정 노출, 송금 딥링크 우선 |
| 기존 이메일 가입 코드가 전환 중 남아 혼선 | MVP 구현 순서 0단계에서 먼저 정리, 이메일 가입 경로는 배포 전 완전 제거 |

## 10. 결정 사항 & 오픈 이슈

### 결정 사항

| 항목 | 결정 | 영향 |
|---|---|---|
| 로그인 | **카카오 로그인 단독** | 기존 이메일 회원가입 → 카카오 기반으로 전환(7장 전환 계획), 비로그인 게스트는 P2로 미룸 |

| 벌칙 금액 | **고정 금액 + 비율 둘 다** (전액은 비율 100% 프리셋) | 4.5 벌칙 정산 규칙 참고 |
| 장소 결정 | **차수별 장소 + 후보 투표, 카카오 로컬 API로 검색** | Round에 장소 상태 추가, 백엔드에 카카오 로컬 프록시 필요 |

| 벌칙 금액 결정 시점 | **게임은 벌칙자만 정하고, 금액 조건은 게임 후·지출 등록 뒤 호스트가 설정** | R-4·R-5 재정의, R-9 신설. `PenaltyRule`은 게임 후 생성(게임당 1개), `Penalty` 상태 `ASSIGNED/APPLIED/WAIVED/VOIDED`로 재정의(기존 `PENDING` 폐지). `targetExpense`는 기존 지출만 |
| 미설정 벌칙과 정산 확정 | **조건 미설정(`ASSIGNED`) 금액형 벌칙이 있으면 확정 불가** — "조건 입력" 또는 "금액 벌칙 없음(`WAIVED`)" 중 선택. 진행 중(`WAITING`/`PLAYING`) 금액형 게임이 있어도 확정 불가, 경고는 `acknowledgeWarnings=true`로 확인 | S-10 신설. 행동형 벌칙은 영향 없음. 재확정에도 같은 검사 |
| 한 규칙에 벌칙자 여러 명 (N1) | **각자 적용** (예: `RATIO 30%` × 2명 → 각자 30%). ~~같은 규칙 내 순서는 `Penalty.id`~~ → 같은 규칙 벌칙자는 순서 없이 잔액 초과 시 균등 분할(D3) | 예 5-a·5-b |
| 적용 순서 (N2) | **게임 결과 공개 시각(`applyOrderAt`) → 원 회차 `GameSession.id`(동시각 타이브레이크)** 순으로 규칙 단위 적용. 다시 돌린 회차는 원 회차의 `applyOrderAt` 상속. (기존 2순위 `Penalty.id`는 D3로 초과분 차감 순서 용도로만 축소) | `PenaltyRule.applyOrder` 저장 필드 폐지, 정렬 키로 파생, `applyOrderAt`은 `DATETIME(6)` |
