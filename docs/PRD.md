# moyeo PRD — 친구 모임 관리 웹앱

## Context

친구 모임은 보통 **1차 밥 → 2차 볼링 or 보드게임** 패턴으로 굴러간다. 이때 매번 반복되는 귀찮음이 있다.

- 단톡방에서 "누구 와?" 물어보고 답 안 하는 사람 쫓아다니기
- "어디서 볼까?" 하면 맛집 링크만 수십 개 쏟아지고 결정은 흐지부지, 2차 장소는 당일에 급하게 찾기
- 1차만 온 사람, 2차부터 온 사람 섞여서 정산이 꼬임
- "꼴찌가 2차 쏘기" 같은 벌칙을 하지만 결과가 정산에 수동으로 반영됨
- 사다리·꽝뽑기는 각자 다른 앱을 켜서 하고, 기록은 안 남음

**한 줄 정의:** "모임 공지 → 장소 정하기 → 참석 → 놀기(게임) → 정산"을 **하나의 링크**로 끝내는 모바일 웹앱.

**핵심 차별점:** **게임 결과가 정산에 자동으로 연결된다.** (토스 N빵·사다리 앱 같은 단일 기능 앱과의 차이)

## 1. 목표 & 지표

| 구분 | 목표 | 지표 (측정 방법) |
|---|---|---|
| 참석 확인 | 단톡방 "누구 와?" 제거 | 모임 생성 후 24h 내 응답률 ≥ 80% (`Attendance` 응답 시각 기준) |
| 장소 결정 | 단톡방 "어디서 봐?" 제거 | 투표 시작 → 장소 확정까지 시간 중앙값, 투표 참여율(투표한 멤버 ÷ 그룹 멤버) |
| 정산 | 모임 끝나고 10분 안에 정산 완료 | 모임 종료(마지막 차수 종료) → 정산 확정까지 시간 중앙값 ≤ 10분 |
| 재미 | 게임을 moyeo 안에서 | 모임당 게임 실행 횟수, 게임→정산 연동 비율(금액형 벌칙이 `APPLIED`된 게임 ÷ 전체 게임) |
| 리텐션 | 같은 그룹의 재사용 | 그룹당 월 모임 생성 수, 4주 재방문율 |

**Non-goal (지금은 안 함):**
- 장소 예약/결제 대행 — 장소를 *정하는* 것까지만, 예약은 사용자가 직접
- 공개 모임 매칭(소모임·문토류)
- 채팅 기능 — 단톡방 대체 X, 단톡방에 링크를 뿌리는 구조

## 2. 타겟 & 페르소나

| 페르소나 | 특징 | 이탈 요인 / 대응 |
|---|---|---|
| **총무형(호스트)** — 핵심 사용자 | 모임 만들고 정산까지 떠안는 사람. 가장 큰 페인 보유 | 정산이 수동이면 안 씀 → 벌칙 자동 반영·송금 최소화 |
| **참여형(게스트)** | 링크 눌러 참석만 누르고 싶은 사람 | **가입 폼을 강요하면 이탈** → 카카오 원탭 로그인으로 진입 비용 최소화 |

- 규모: 4~12명 고정 친구 그룹, 월 1~4회 모임.

## 3. 핵심 사용자 흐름

```
[호스트] 그룹 생성 → 모임 생성(날짜/차수) → 차수별 장소 바로 지정 or 후보 투표 열기 → 카톡으로 링크 공유
[게스트] 링크 접속 → 카카오 로그인(원탭) → 그룹 자동 가입 → 차수별 참석 응답 + 장소 후보 추가·투표
        ↓ (마감 전 미응답자 리마인드, 투표 마감 시 장소 자동 확정)
[당일]  체크인 → 1차 지출 등록 → 2차 볼링 점수 입력 / 사다리·꽝뽑기
        ↓ (게임 결과 → "벌칙: OO가 2차 50% 부담" 자동 반영)
[종료]  정산 확정 → 송금 링크 공유 → 입금 체크 → 기록/명예의 전당
```

## 4. 기능 요구사항

우선순위: **P0 = MVP 필수 / P1 = 출시 직후 / P2 = 이후**. 기능 ID는 다른 문서·태스크가 참조하므로 재번호하지 않는다(표 순서 ≠ 번호 순서일 수 있음).

### 4.1 그룹(크루)

| ID | 기능 | 우선순위 |
|---|---|---|
| G-1 | 그룹 생성, 초대 링크 발급(만료/재발급) | P0 |
| G-2 | 멤버 목록, 그룹 내 닉네임/프로필 이모지 | P0 |
| G-3 | **카카오 로그인** 후 초대 링크로 그룹 자동 가입(카카오 닉네임·프로필 기본값, 그룹 내 닉네임 변경 가능) | P0 |
| G-4 | 역할: 방장 / 총무 / 멤버 | P1 |
| G-5 | 그룹 기본 송금 계좌·토스/카카오페이 링크 저장 | P1 |
| G-6 | 카카오 계정 없는 친구용 임시 게스트(닉네임 + 기기 토큰, 참석 응답만 가능) | P2 |

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| G-1 | Given 로그인한 사용자 / When 그룹을 생성하면 / Then 생성자는 그 그룹 멤버가 되고 만료 시각이 있는 초대 링크 토큰이 발급된다. Given 초대 링크를 재발급하면 / Then 이전 토큰으로 접속 시 "만료된 링크" 응답을 받는다. |
| G-2 | Given 그룹 멤버 / When 멤버 목록을 조회하면 / Then 각 멤버의 그룹 내 닉네임·프로필 이모지가 반환되고, 비멤버가 조회하면 403을 받는다. |
| G-3 | Given 미로그인 사용자가 유효한 초대 링크로 접속 / When 카카오 로그인을 마치면 / Then 원래 초대 링크로 돌아가 그룹에 자동 가입되고 그룹 닉네임 기본값은 카카오 닉네임이다. Given 이미 가입된 멤버 / When 같은 링크로 다시 들어오면 / Then 중복 가입 없이 그룹 홈으로 이동한다. |

### 4.2 모임 & 참석

| ID | 기능 | 우선순위 |
|---|---|---|
| M-1 | 모임 생성: 제목, 날짜·시간, 메모 (장소는 차수별로 정함 — 4.3 참고) | P0 |
| M-2 | **차수(라운드) 구성**: 1차 밥 / 2차 볼링 / 3차 보드게임 등 템플릿 제공 | P0 |
| M-3 | **차수별 참석 응답**: 참석 / 불참 / 미정 + "늦참(2차부터)", "1차만" | P0 |
| M-4 | 응답 마감 시간, 현황판(누가 왔고 누가 안 눌렀는지) | P0 |
| M-5 | 날짜 후보 투표(When2meet식) — 날짜 미정일 때 | P1 |
| M-6 | 미응답자 리마인드(카톡 공유 문구 생성 / 웹 푸시) | P1 |
| M-7 | 당일 체크인(도착 체크) → 실제 참석자 확정 | P1 |
| M-8 | 노쇼 기록 → 통계 반영 | P2 |

> 설계 포인트: **참석 데이터 = 정산 데이터의 기본값.** 차수별 참석자가 그대로 정산 분배 대상이 된다.

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| M-1 | Given 그룹 멤버 / When 제목·날짜·시간·메모로 모임을 생성하면 / Then 모임이 그룹에 등록되고 모임 상세 링크가 반환된다. 제목·날짜 누락 시 400과 필드 에러를 받는다. |
| M-2 | Given 모임 생성 화면 / When "밥→볼링" 템플릿을 고르면 / Then 1차(밥)·2차(볼링) 차수가 순서대로 생성되고, 각 차수의 장소 상태는 `UNDECIDED`다. |
| M-3 | Given 차수가 2개인 모임 / When 멤버가 "늦참(2차부터)"을 고르면 / Then 1차는 불참, 2차는 참석으로 저장된다. "1차만"은 그 반대로 저장된다. 같은 멤버가 다시 응답하면 기존 응답이 갱신된다(차수당 1건). |
| M-4 | Given 응답 마감 시간이 지난 모임 / When 멤버가 응답을 바꾸려 하면 / Then 거부된다(호스트 대리 수정은 허용). 현황판은 차수별로 참석/불참/미정/미응답 멤버 목록을 보여준다. |

### 4.3 장소 결정

| ID | 기능 | 우선순위 |
|---|---|---|
| P-1 | **장소 검색·후보 등록**: 카카오 로컬 검색으로 장소 검색(이름·주소·카테고리·좌표·카카오맵 링크 자동 채움), 검색 안 되면 이름 + 지도 링크 직접 입력 | P0 |
| P-2 | **차수별 장소 정하기**: 호스트가 바로 확정하거나, 후보 투표를 연다. 투표 중엔 멤버 누구나 후보 추가 가능 | P0 |
| P-3 | **후보 투표**: 복수 선택 가능, 득표 현황 실시간 갱신(누가 어디 찍었는지 공개) | P0 |
| P-4 | **마감 & 확정**: 투표 마감 시 최다 득표 후보 자동 확정, 호스트는 언제든 수동 확정/재투표 가능. 동점이면 호스트가 고름 | P0 |
| P-5 | 확정 장소 노출: 모임 상세·카톡 공유 문구·OG 미리보기에 반영, 카카오맵 길찾기 링크 | P0 |
| P-6 | 동점 시 룰렛으로 결정(R-3 연동, 결과 이력 공개) | P1 |
| P-7 | **2차 장소 추천**: 확정된 1차 장소 반경 N m 안의 볼링장·보드게임카페·술집을 카테고리 검색으로 후보 제안 | P1 |
| P-8 | 그룹 단골 장소 저장, 지난 모임 장소에서 바로 후보로 불러오기 | P1 |
| P-9 | 행동형 벌칙 "다음 모임 장소 정하기" 당첨자에게 다음 모임 1차 장소 확정 권한 부여 | P2 |
| P-10 | **중간 지점 추천**: 참석자가 출발지(동네 수준)를 선택 입력 → 중간 지점 근처 후보 제안 | P2 |

> 설계 포인트: **장소는 모임이 아니라 차수(Round)에 붙는다.** 1차 밥집, 2차 볼링장이 다르기 때문. 차수마다 `UNDECIDED(미정) → VOTING(투표 중) → CONFIRMED(확정)` 상태를 따로 갖는다.

**장소 도메인 규칙**
- **스냅샷:** 장소 정보는 카카오 place id와 함께 **확정 시점의 이름·주소·좌표를 스냅샷으로 저장**한다(가게가 이름을 바꾸거나 폐업해도 기록은 유지). 저장 범위는 카카오 API 약관 확인 필요(오픈 이슈 5).
- **카카오 로컬 프록시:** 장소 검색은 **백엔드가 카카오 로컬 REST API를 프록시**한다(REST 키를 클라이언트에 노출하지 않고, 호출량 제한·캐싱을 서버에서 관리). 지도 표시는 SPA에서 카카오맵 JS SDK로 한다.
- **동시성:** 투표는 `(후보, 멤버)` **유니크 제약**으로 중복을 막고, 마감 처리와 수동 확정이 겹치면 `Round.version` **낙관적 락**으로 먼저 들어온 쪽만 반영한다.
- 상태 전이: `UNDECIDED → CONFIRMED`(바로 확정), `UNDECIDED → VOTING → CONFIRMED`(투표), `CONFIRMED → VOTING`(재투표, 호스트만).

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| P-1 | Given 검색어 "강남 볼링" / When 장소를 검색하면 / Then 서버가 카카오 로컬 API를 호출해 이름·주소·카테고리·좌표·지도 링크 목록을 반환한다(클라이언트 응답·네트워크에 REST 키 없음). Given 카카오 API 실패·쿼터 초과 / When 검색하면 / Then 직접 입력 폴백 안내를 받고 이름 + 지도 링크로 후보를 등록할 수 있다. |
| P-2 | Given `UNDECIDED` 차수 / When 호스트가 장소를 바로 지정하면 / Then 후보 1개짜리 `PlaceCandidate`가 생성되고 차수는 `CONFIRMED`가 된다. When 호스트가 투표를 열면 / Then 차수는 `VOTING`이 되고 마감 시각이 필수로 저장되며, 그룹 멤버 누구나 후보를 추가할 수 있다. |
| P-3 | Given `VOTING` 차수 / When 멤버가 후보 2곳에 투표하면 / Then 두 표가 저장되고 WebSocket으로 득표 수·투표자 목록이 모든 접속자에게 갱신된다. 같은 후보에 다시 투표하면 표는 1개로 유지된다(유니크 제약). |
| P-4 | Given 마감 시각이 지난 `VOTING` 차수, 최다 득표 후보가 1개 / When 마감 처리가 실행되면 / Then 그 후보로 `CONFIRMED` 된다. 동점이면 `VOTING`을 유지한 채 호스트에게 선택을 요청한다. 마감 처리와 호스트 수동 확정이 동시에 들어오면 하나만 반영되고 다른 요청은 충돌 응답을 받는다. |
| P-5 | Given 1차 장소가 확정된 모임 / When 모임 링크의 OG 메타를 요청하면 / Then 미리보기 설명에 확정 장소 이름이 포함되고, 모임 상세에 카카오맵 길찾기 링크가 노출된다. |

### 4.4 게임 & 벌칙

| ID | 기능 | 우선순위 |
|---|---|---|
| R-0 | **게임 방(로비)**: 진행자가 게임 생성 → 참가자 각자 폰으로 입장 → 전원 준비 시 시작 | P0 |
| R-1 | **사다리 타기**: 참가자 자동 로드, 결과 항목 입력(꽝/벌칙/당첨), 모두의 폰에서 같은 애니메이션 동시 재생 | P0 |
| R-2 | **꽝뽑기(제비뽑기)**: N장 중 꽝 K장, 각자 자기 폰에서 카드 1장 선택 → 전원 뽑으면 동시 공개 | P0 |
| R-3 | 룰렛 / 랜덤 순서 정하기(볼링 레인 순서, 보드게임 선) | P1 |
| R-4 | **벌칙 프리셋**: 금액형(고정 금액 / 비율 — 4.5 벌칙 정산 규칙 참고)·행동형("다음 모임 장소 정하기·예약", P-9 연동) | P0 |
| R-5 | **게임 결과 → 정산 연동**: 금액형 벌칙 당첨 시 해당 차수 정산에 자동 반영 | P0 |
| R-6 | 볼링 점수 입력 → 순위 산출 → 꼴찌/하위 N명 자동 벌칙 | P1 |
| R-7 | 보드게임 승패 기록(게임명, 순위) | P1 |
| R-8 | 이탈자 처리: 제한 시간 내 안 뽑으면 남은 카드 자동 배정, 재접속 시 상태 복구 | P0 |

> 설계 포인트: **게임 진행 방식은 각자 폰.** 게임 상태(`WAITING` 대기 → `PLAYING` 진행 → `REVEALED` 공개 → `CLOSED` 종료)는 서버가 관리하고 WebSocket으로 모든 참가자에게 브로드캐스트한다.

**공정성 요구사항 (중요)**
- 결과(사다리 연결, 카드 배치)는 **게임 시작 시점에 서버에서 생성**하고, 클라이언트에는 공개 시점 전까지 보내지 않는다.
- 꽝뽑기에서 "카드를 고르는 행위"는 연출이고, 실제 결과는 서버가 미리 섞어둔 배열의 위치로 결정된다. 같은 카드를 동시에 고르면 먼저 도착한 요청이 가져간다(**낙관적 락**).
- 실행 시각·참가자·결과를 기록으로 남기고, "다시 돌리기"는 가능하되 **재실행 이력이 모두에게 보인다** (조작 의심 방지 = 친구 사이 신뢰).

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| R-0 | Given 진행자가 만든 `WAITING` 게임 방 / When 참가자 전원이 준비를 누르면 / Then 진행자가 시작할 수 있고 상태가 `PLAYING`으로 바뀌어 모든 참가자에게 브로드캐스트된다. 준비 안 한 참가자가 있으면 시작 요청은 거부된다. |
| R-1 | Given 참가자 4명·결과 항목 4개 / When 게임이 시작되면 / Then 서버가 사다리 연결을 생성·저장하고, `REVEALED` 전까지 어떤 클라이언트 응답·WebSocket 메시지에도 연결 정보가 포함되지 않는다. 공개 시 모든 참가자가 같은 연결 데이터를 받는다. |
| R-2 | Given N=5, K=1 꽝뽑기 / When 두 참가자가 같은 카드를 동시에 고르면 / Then 먼저 도착한 요청만 성공하고 다른 쪽은 "이미 선택됨" 응답을 받는다. 전원이 뽑으면 상태가 `REVEALED`가 되고 결과가 동시에 공개된다. |
| R-4 | Given 게임 생성 화면 / When 벌칙 프리셋으로 `RATIO 30%`·대상 2차를 고르면 / Then 게임에 벌칙 정의(유형·비율·대상)가 저장된다. 비율은 1~100%, 고정 금액은 1원 이상 정수만 허용한다. |
| R-5 | Given 금액형 벌칙이 걸린 게임 / When 결과가 공개되면 / Then 당첨자에게 `Penalty`가 생성되고, 대상 지출이 있으면 `APPLIED`, 없으면 `PENDING`으로 저장된다. "다시 돌리기"를 하면 이전 회차 벌칙은 무효 처리되고 이력에 남는다. |
| R-8 | Given 제한 시간이 있는 꽝뽑기 / When 제한 시간이 지나도 안 뽑은 참가자가 있으면 / Then 서버가 남은 카드를 자동 배정하고 공개한다. Given 연결이 끊긴 참가자 / When 재접속하면 / Then REST로 현재 게임 상태(본인 선택 포함, 공개 전 결과 제외)를 받아 화면을 복구한다. |

### 4.5 정산

| ID | 기능 | 우선순위 |
|---|---|---|
| S-1 | 차수별 지출 등록: 금액, 결제자, 메모(영수증 사진 P1) | P0 |
| S-2 | 분배 기본값 = 해당 차수 참석자 N빵 | P0 |
| S-3 | 개별 조정: 특정인 제외, 고정 금액, 비율(술 안 마심 등) | P0 |
| S-4 | 벌칙 반영 내역 표시("민수: 사다리 꽝 → 2차 +30,000원") | P0 |
| S-5 | **송금 최소화**: 누가 누구에게 얼마 보내면 끝나는지 최소 송금 경로 계산 | P0 |
| S-6 | 송금 체크(보냈어요 → 받은 사람 확인), 미입금 리마인드 | P0 |
| S-7 | 토스/카카오페이 송금 딥링크, 계좌 복사 | P1 |
| S-8 | 원 단위 처리 규칙(100원 단위 올림, 올림으로 더 걷힌 금액은 결제자 몫에서 차감) | P0 |
| S-9 | 회비 통장 모드(그룹 잔액 관리) | P2 |

**벌칙 정산 규칙 (고정 금액 + 비율 둘 다 지원)**

| 유형 | 의미 | 예시 |
|---|---|---|
| `FIXED_AMOUNT` | 정해진 금액을 벌칙자가 부담 | "꽝 걸린 사람 2만원 부담" |
| `RATIO` | 대상 금액의 N%를 벌칙자가 부담 | "꼴찌가 2차 30% 부담" |
| `FULL` | 대상 금액 전부 부담 (`RATIO 100%`의 단축 프리셋) | "꼴찌가 2차 쏘기" |

- **대상 범위:** 차수 전체(예: 2차 볼링 총액) 또는 특정 지출 항목(예: 2차 음료값)을 고른다.
- **나머지 분배:** 벌칙자 부담분을 먼저 떼고, 남은 금액은 **벌칙자를 뺀** 참석자끼리 기본 분배 규칙대로 나눈다(오픈 이슈 2).
- **상한:** 고정 금액이 대상 금액보다 크면 대상 금액까지만 부담한다(그 차수에서 남이 돈을 받는 일은 없음).
- **벌칙 여러 개:** 같은 대상에 벌칙이 여러 개면 적용 순서대로 차감하고, 벌칙 합계는 대상 금액을 넘을 수 없다. 넘으면 정산 확정 전에 경고한다.
- **지출 등록 전 벌칙:** 게임이 지출보다 먼저 끝나도 벌칙은 "대기"(`PENDING`) 상태로 저장했다가 대상 지출이 등록되면 자동 적용(`APPLIED`)된다.

**원 단위 처리 규칙 (S-8)**
- 1인 부담액 = 분배 대상 금액 ÷ 인원 → **100원 단위 올림**.
- 올림으로 더 걷힌 금액(`1인 부담액 × 인원 − 분배 대상 금액`)은 **결제자 몫에서 차감**해 총액을 정확히 맞춘다.
- 비율 벌칙 부담액도 계산 후 같은 규칙(100원 단위 올림)을 적용한다.

**정산 계산 순서**
1. 차수별(또는 지출 항목별) 지출 합계
2. 벌칙 부담분 차감(`FIXED_AMOUNT`/`RATIO`/`FULL`, 상한 적용)
3. 남은 금액을 벌칙자 제외 참석자에게 기본 분배(가중치/제외 반영)
4. 결제자별 받을 돈 − 낼 돈 = 순잔액
5. 송금 최소화 알고리즘으로 송금 목록 생성

**계산 예시 (검산 완료)**

예 1) `RATIO` — 2차 참석 4명(철수·민수·영희·지수), 지출 100,000원, 결제자 철수, 민수 `RATIO 30%`

| 단계 | 계산 | 결과 |
|---|---|---|
| 2. 벌칙 부담 | 100,000 × 30% | 민수 30,000원 |
| 3. 나머지 분배 | 70,000 ÷ 3 = 23,333.3… → 100원 올림 | 1인 23,400원 |
| S-8 초과분 | 23,400 × 3 − 70,000 | 200원 → 결제자 철수 몫에서 차감 → 철수 23,200원 |
| 합계 검산 | 30,000 + 23,200 + 23,400 + 23,400 | 100,000원 ✓ |
| 4. 순잔액 | 철수 100,000 − 23,200 | 철수 +76,800 / 민수 −30,000 / 영희 −23,400 / 지수 −23,400 (합 0 ✓) |
| 5. 송금 | — | 민수→철수 30,000, 영희→철수 23,400, 지수→철수 23,400 (합 76,800 ✓) |

예 2) `FIXED_AMOUNT` — 같은 조건, 민수 고정 20,000원
- 나머지 80,000 ÷ 3 = 26,666.6… → 26,700원. 초과분 26,700 × 3 − 80,000 = 100원 → 철수 26,600원.
- 검산: 20,000 + 26,600 + 26,700 + 26,700 = 100,000원 ✓

예 3) 상한 — 같은 조건, 민수 고정 150,000원
- 대상 금액 100,000원까지만 부담 → 민수 100,000원, 나머지 3명 0원.

**수용 기준 (P0)**

| ID | Given / When / Then |
|---|---|
| S-1 | Given 2차 차수 / When 금액 100,000원·결제자 철수로 지출을 등록하면 / Then 지출이 저장되고 해당 차수의 `PENDING` 벌칙이 있으면 `APPLIED`로 바뀐다. 금액이 0 이하이거나 정수가 아니면 400을 받는다. |
| S-2 | Given 2차 참석자 4명, 지출 100,000원, 벌칙 없음 / When 정산을 계산하면 / Then 4명 모두 25,000원이 배정되고 불참자는 분배 대상에 없다. |
| S-3 | Given 참석자 4명 중 지수를 제외 / When 정산을 계산하면 / Then 지수 부담액은 0원이고 나머지 3명이 나눈다(S-8 적용). 가중치(비율) 조정 시 가중치에 비례해 배정된다. |
| S-4 | Given 민수에게 2차 `RATIO 30%` 벌칙이 `APPLIED` / When 정산 탭을 조회하면 / Then "민수: 사다리 꽝 → 2차 +30,000원" 형식으로 벌칙 출처(게임)·대상·금액이 항목별로 노출된다. |
| S-5 | Given 예 1의 순잔액 / When 송금 목록을 생성하면 / Then 송금 건수 3건, 금액 합 76,800원인 목록이 나오고 모든 멤버의 순잔액이 송금 후 0이 된다. 송금 건수는 (순잔액이 0이 아닌 인원 − 1) 이하다. |
| S-6 | Given 확정된 정산의 송금 1건 / When 보낸 사람이 "보냈어요"를 누르고 받는 사람이 확인하면 / Then `sentAt`·`confirmedAt`이 순서대로 기록되고, 받는 사람 확인 없이 `confirmedAt`은 기록되지 않는다. |
| S-8 | Given 예 1 조건 / When 정산을 계산하면 / Then 영희·지수 23,400원, 철수 23,200원, 민수 30,000원이고 부담액 합이 지출 합계 100,000원과 정확히 같다. |

## 6. 비기능 요구사항

| 영역 | 요구사항 |
|---|---|
| 플랫폼 | **모바일 웹 우선 + PWA**(홈 화면 추가, 웹 푸시). 앱 설치 강요 안 함 |
| 공유 | **카카오톡 공유**(OG 태그 미리보기: "토요일 모임 · 강남 OO식당 · 5/8명 참석") — 바이럴 핵심 경로 |
| 구조 | **SPA + REST API.** Spring Boot는 JSON API와 WebSocket만 맡고, 화면은 별도 SPA(React 계열)가 담당. OG 태그는 SPA가 못 만들어주니까 초대/모임 링크 경로는 서버에서 OG 메타만 담은 HTML을 내려준다 |
| 인증 | **카카오 로그인(OAuth2).** 백엔드가 카카오 인가 코드를 받아 회원 조회/생성 후 자체 토큰(Access + Refresh, `HttpOnly` 쿠키) 발급. 카카오톡 인앱 브라우저에서 로그인이 깨지지 않는지 꼭 확인 |
| 인가 | 초대 링크로 들어온 사람은 로그인 직후 원래 링크로 돌아가 그룹에 자동 가입. 그룹 리소스는 그룹 멤버만 접근. 금융 정보(계좌)는 그룹 멤버에게만 노출 |
| 실시간 | **MVP부터 WebSocket(STOMP)** — 게임 방(로비/진행/공개)은 필수. 참석 현황·장소 투표 현황·정산 현황 갱신도 같은 채널 사용. 끊겼다 다시 붙으면 REST로 현재 상태를 받아 복구 |
| 외부 API | **카카오 로컬(장소 검색)** — 서버에서 호출, 검색 결과 단기 캐싱, 일일 쿼터 초과 시 직접 입력(P-1)으로 폴백 |
| 금액 처리 | 금액은 정수(원, `long`) 처리, 부동소수점 금지. 비율 벌칙은 계산 후 원 단위 처리 규칙(S-8) 적용. 정산 확정 후 수정 시 이력 남김 |
| 트랜잭션·동시성 | 정산/게임 결과 저장은 트랜잭션 처리, 동시 응답 충돌 시 낙관적 락 (아래 표) |

**아키텍처 방침 (CLAUDE.md 반영)**
- Spring Boot 4.1 + Java 21, Gradle 9, MySQL, Spring Data JPA.
- 레이어드 아키텍처: **Controller → Service → Repository**. 계층 간 전달은 **DTO**, 엔티티를 API 응답으로 직접 노출하지 않음.
- 생성자 주입(`@RequiredArgsConstructor`), 트랜잭션 경계는 **Service 계층 `@Transactional`**.
- **일관된 API 응답·예외 구조:** 모든 REST 응답은 공통 래퍼(예: `{ success, data, error: { code, message } }`)로 통일하고, `@RestControllerAdvice`가 `BusinessException(ErrorCode)`·검증 실패·락 충돌·유니크 위반을 공통 에러 응답으로 변환한다.
- 정산 계산은 JPA·Spring에 의존하지 않는 **순수 도메인 로직**으로 분리해 단위 테스트를 촘촘히 붙인다.

**동시성·락 전략**

| 대상 | 충돌 상황 | 전략 |
|---|---|---|
| 참석 응답 (M-3) | 같은 멤버 중복 응답 | `(round, member)` 유니크 제약 + upsert |
| 그룹 가입 (G-3) | 같은 링크 동시 클릭 | `(group, member)` 유니크 제약 |
| 장소 투표 (P-3) | 중복 투표 | `(candidate, member)` 유니크 제약 |
| 장소 확정 (P-4) | 자동 마감 vs 수동 확정 | `Round.version` 낙관적 락, 늦은 쪽 409 |
| 꽝뽑기 선택 (R-2) | 같은 카드 동시 선택 | `(gameSession, pickedSlot)` 유니크 제약 + `GameSession.version` 낙관적 락, 먼저 도착한 요청만 성공 |
| 게임 상태 전이 (R-0/R-8) | 시작·공개·자동 배정 경합 | `GameSession.version` 낙관적 락 |
| 정산 확정·송금 체크 (S-6) | 동시 확정/수정 | `Settlement.version` 낙관적 락 |

## 7. 데이터 모델 초안

```
Member(kakaoId) ─┬─< GroupMember(nickname, emoji, role) >── Group ─< InviteLink (token, expiresAt)
                 │     ※ (group, member) 유니크          ├─< FavoritePlace (Place 스냅샷, P1)
                 │                                       └─< Meeting(title, startAt, memo, responseDeadline)
                 │                                             └─< Round(차수: 밥/볼링/보드게임, seq,
                 │                                                 │   placeStatus: UNDECIDED/VOTING/CONFIRMED,
                 │                                                 │   placeVoteDeadline, confirmedCandidate, version)
                 │                                                 ├─< PlaceCandidate (kakaoPlaceId?, Place{name, address, lat, lng,
                 │                                                 │     │             category, mapUrl}, proposedBy)
                 │                                                 │     └─< PlaceVote (member)  ※ (candidate, member) 유니크
                 │                                                 ├─< Attendance (member, status: ATTEND/ABSENT/UNDECIDED, checkedIn)
                 │                                                 │     ※ (round, member) 유니크
                 │                                                 ├─< Expense (payer, amount, memo)
                 │                                                 │     └─< ExpenseShare (member, amount, weight, excluded)
                 │                                                 └─< GameSession (type: LADDER/DRAW/ROULETTE/BOWLING,
                 │                                                       │           status: WAITING/PLAYING/REVEALED/CLOSED,
                 │                                                       │           seed/결과 배열(공개 전 비노출), rerunOf?, version)
                 │                                                       ├─< GameParticipant (member, ready, pickedSlot)
                 │                                                       │     ※ (gameSession, pickedSlot) 유니크
                 │                                                       ├─< GameResult (member, outcome, rank/score)
                 │                                                       └─> Penalty (kind: MONEY/ACTION,
                 │                                                                    moneyType: FIXED_AMOUNT/RATIO/FULL,
                 │                                                                    amount | ratio, targetRound | targetExpense,
                 │                                                                    applyOrder, status: PENDING/APPLIED)
                 └─ Settlement (meeting, status, confirmedAt, version) ─< Transfer (from, to, amount, sentAt, confirmedAt)
```

**설계 메모**
- 그룹 안에서의 닉네임은 `GroupMember`에 따로 둔다(그룹마다 다른 별명 가능).
- 호스트가 투표 없이 바로 장소를 정해도 후보 1개짜리로 `PlaceCandidate`를 만들고 `CONFIRMED` 처리한다(확정 장소 조회 경로를 하나로 통일). 이름·주소·좌표는 공통 `Place` **임베디드 값 타입**으로 묶어 `PlaceCandidate`·`FavoritePlace`에서 재사용.
- 장소는 확정 시점 스냅샷(카카오 place id + 이름·주소·좌표)으로 저장한다(4.3 장소 도메인 규칙).
- "다시 돌리기"는 새 `GameSession`을 만들고 `rerunOf`로 이전 회차를 가리켜 재실행 이력을 보존한다. 이전 회차의 `Penalty`는 무효 처리한다.
- `Penalty.applyOrder`는 같은 대상에 벌칙이 여러 개일 때 차감 순서를 정한다.
- 정산 확정 후 수정 이력 저장 방식(별도 이력 테이블 vs 스냅샷 JSON)은 오픈 이슈 9.

**현재 코드와의 차이 → 전환 계획**

현재 `src/main/java/com/poco7250/moyeo`에는 이메일·비밀번호 회원가입 기반 코드가 있다. **카카오 로그인 단독** 결정(10장)에 따라 아래처럼 전환한다.

| 현재 코드 | 문제 | 전환 계획 |
|---|---|---|
| `member/domain/Member` — `email`(필수·유니크), `password`(BCrypt), `nickname`(유니크) | 카카오 로그인엔 비밀번호가 없고, 이메일은 카카오 동의 항목이라 없을 수 있음. 카카오 닉네임은 중복 가능 | `password` 제거, `kakaoId`(유니크) 추가, 닉네임·프로필 이미지 저장, `email`은 nullable, `nickname` 유니크 제약 제거(그룹 닉네임은 `GroupMember`) |
| `member/service/MemberService.join` (이메일·닉네임 중복 검사 + 비밀번호 암호화) | 회원가입 흐름 자체가 없어짐 | 카카오 인가 코드 → 회원 조회/생성(`findOrCreateByKakaoId`) → 자체 토큰 발급 서비스로 교체 |
| `member/controller/MemberController` — `@Controller` + 서버 렌더링 회원가입 폼(`member/joinForm`) | SPA + REST API 결정과 어긋남 | `@RestController` 기반 인증 API(카카오 콜백, 토큰 재발급, 내 정보)로 교체, 회원가입 폼·뷰 제거 |
| `member/dto/MemberJoinRequest` | 이메일·비밀번호 입력 DTO | 제거, 카카오 사용자 정보·로그인 응답 DTO로 대체 |
| `global/config/PasswordEncoderConfig` (BCrypt `PasswordEncoder` 빈) | 비밀번호를 안 씀 | **제거**. 대신 OAuth2 클라이언트·토큰 설정으로 대체 |
| `global/error/ErrorCode` — `DUPLICATE_EMAIL`, `DUPLICATE_NICKNAME` | 이메일 가입 전용 에러 | 제거, 인증·도메인 에러 코드 추가 |
| `global/error/GlobalExceptionHandler` — `@ControllerAdvice` + `ModelAndView` 에러 페이지 | JSON API에 HTML 에러 페이지를 내려줌 | `@RestControllerAdvice` + 공통 에러 응답(JSON)으로 전환. `DataIntegrityViolationException`→409 처리는 유지 |

## 10. 결정 사항 & 오픈 이슈

### 결정 사항

| 항목 | 결정 | 영향 |
|---|---|---|
| 로그인 | **카카오 로그인 단독** | 기존 이메일 회원가입 → 카카오 기반으로 전환(7장 전환 계획), 비로그인 게스트는 P2로 미룸 |
| 프론트엔드 | **SPA + REST API** | 백엔드는 JSON API·WebSocket 전용, OG 태그용 서버 렌더링 경로 별도 |
| 게임 진행 | **각자 폰** | MVP부터 WebSocket 필수, 게임 상태 머신·이탈 처리 필요 |
| 벌칙 금액 | **고정 금액 + 비율 둘 다** (전액은 비율 100% 프리셋) | 4.5 벌칙 정산 규칙 참고 |
| 장소 결정 | **차수별 장소 + 후보 투표, 카카오 로컬 API로 검색** | Round에 장소 상태 추가, 백엔드에 카카오 로컬 프록시 필요 |

### 오픈 이슈

| # | 이슈 | 선택지 / 현재 안 |
|---|---|---|
| 1 | SPA 프레임워크 | React(Vite) vs Next.js. OG 태그와 배포 방식에 영향 |
| 2 | 비율 벌칙에서 벌칙자가 나머지 금액 분배에서도 빠지는 게 맞는지 | 현재 안: 빠짐 / 대안: 옵션으로 둠 |
| 3 | 송금 딥링크 | 토스/카카오페이 송금 링크의 정책·제약 확인 필요 |
| 4 | 장소 투표 방식 | 복수 선택(현재 안) vs 1인 1표. 복수 선택이면 "아무데나 다 좋아"가 결과를 흐릴 수 있음 |
| 5 | 카카오 로컬 API 약관 | 장소 정보(이름·주소·좌표)를 DB에 영구 저장해도 되는 범위 확인 필요 |
| 6 | 장소 투표를 참석 응답과 묶을지 | 해당 차수 "불참"이면 투표 못 하게 막을지. 현재 안: 그룹 멤버 누구나 투표 |
| 7 | 복수 벌칙에서 `RATIO`의 기준 금액 | 원래 대상 금액 기준 vs 앞 벌칙 차감 후 잔액 기준. 현재 안: 미정("적용 순서대로 차감"만 결정됨) |
| 8 | S-8 초과분 차감 대상이 애매한 경우 | 결제자가 분배 대상에서 제외됐거나 결제자 몫이 초과분보다 작을 때, 지출 결제자가 여럿일 때 누구 몫에서 뺄지. 현재 안: 미정 |
| 9 | 정산 확정 후 수정 이력 저장 방식 | 별도 이력 테이블 vs 확정 시점 스냅샷(JSON). 현재 안: 미정 |
